## Context

The issue is #1052, ask 3, verbatim:

> Gate seats (a security lane, a judge) refuse an untrusted provider, and dsh is untrusted. The only workaround found is a second adapter marked trusted and listed as a judge, which is a blanket trust grant rather than a scoped one. Ask: a documented, scoped way to admit a specific dsh route and model to a specific gate seat, with the measurement or evidence that has to back it. Alternatively, guidance that this should stay impossible, so downstream doesn't build the workaround.

The downstream case is concrete: a DashScope route on dsh, a Qwen Max preview model, serving a workspace-hands security review lane. In this tree that route's abstract model is `qwen-max`, mapped to `dashscope/qwen3.8-max` (`adapters/dsh.json:37`); `dashscope` is not in dsh's `routes` map (`adapters/dsh.json:5-8`), so 0036 ruling 1's absent-declaration default reads it `uncontracted` (`docs/decisions/0036-egress-is-a-property-of-the-route.md:96-104`; `crates/brokkr-runtime/src/agents/load.rs:368-380`). dsh's adapter declares `"trust_tier": "untrusted"` and `"judges": []` (`adapters/dsh.json:3`, `:46`). The compile therefore refuses the seat at the gate before any prompt exists: `refuse_untrusted_gate` reads the tier (`crates/brokkr-runtime/src/bundle/route_policy.rs:48-64`) and `refuse_unjudged_model` reads the judges list (`:66-95`), on every link of a chain (`:29-45`; `crates/brokkr-runtime/src/bundle.rs:2410-2445`).

### The two existing answers

**A work-class panel member under a trusted chief.** The controller's library seats two dsh models as panel members, `bugfix-review-adversarial-dsh` and `bugfix-review-correctness-dsflash`, each `"class": "work"`; the panel's chief is `"class": "gate"` on Claude Fable 5.2, with Opus 5.5 as its fallback (the library text is quoted in this story's commission). This is lawful today: 0021 ruling 1 divides work from gate, 0021 ruling 7 lets a newcomer take work seats freely, and 0041 ruling 3 refuses only a gate link. The panel chief rules; the untrusted member contributes findings, not the verdict. The shipped panel-review recipe is not the same shape — it seats two gate-class members and no chief (`recipes/panel-review/bundle.json:44-54`) — but a work-class member beside a gate-class chief is the existing answer for an untrusted one. An untrusted route can therefore contribute at a gate today, as an advisory member a trusted chief rules on. It cannot be the gate.

**A second adapter marked trusted.** A second adapter file over the same `dsh` driver declares `"trust_tier": "trusted"` and lists the model in `judges`; the gate link then passes both checks. This is the workaround the issue names. It is a blanket grant: one line trusts the whole binary, every route and every model it can reach, now and in future route additions. The copy cannot even keep the model's name: `Adapters::load` refuses one abstract model mapped by two adapters (`crates/brokkr-runtime/src/agents/load.rs:649-663`), so the workaround also renames the abstract model and every agent that hires it. It duplicates the driver, the models map, the credentials and the tool grammar to express a fact about one route and one model, which 0036 already rejected for egress: "Splitting `dsh` into one adapter per route duplicates the binary, the models map and the tool grammar to express a fact about endpoints, and misstates what an adapter is: a provider is a CLI, and this CLI genuinely has one" (`docs/decisions/0036-egress-is-a-property-of-the-route.md:63-66`). Guidance should say not to build it, for the reasons in option E below.

### Why the adapter is too coarse a unit of trust

Decision 0036 moved egress from the adapter to the route because dsh's one declaration fronts three destinations: a local SGLang server on the operator's own DGX Spark, `token-plan.ap-southeast-1.maas.aliyuncs.com` in Alibaba's Singapore region, and the profile's default provider route (`docs/decisions/0036-egress-is-a-property-of-the-route.md:34-44`). The same table is the argument here, on a different axis:

| dsh route | endpoint | where the prompt goes | what the evidence is about |
|---|---|---|---|
| `spark/*` | an SGLang server on the operator's network | the operator's own DGX Spark | local hardware; no third party |
| `dashscope/*` | `token-plan.ap-southeast-1.maas.aliyuncs.com` | Alibaba, Singapore | a third party and a jurisdiction |
| unprefixed (`deepseek-v4-pro`, …) | the profile's default provider route | whatever that profile resolves | an unknown default |

One `trust_tier` line at `adapters/dsh.json:3` answers for all three. But a gate's trust is not one fact: it is the harness release that mediates the prompt, the harness's own native capabilities, the route's provider and jurisdiction, the abstract model's judgment, the role the seat holds, and the box around the hands. They have different evidence, and a route or a model can change while the others stand. The adapter is the right unit for a *tier* — 0021 ruling 2's one grant that a driver may judge — but it is the wrong unit for an exception that names one route and one model. The grant below borrows 0036's route granularity without moving trust onto the route.

### Two words that sound alike: `office` and gate role

Today the tree gives `office` one meaning: the hired agent's name. `crates/brokkr-runtime/src/bundle/tier.rs:9` says "An office is an agent, by name"; `SiteAsks.office` is "the agent's name, or an inline site's authoring label" (`crates/brokkr-runtime/src/capabilities.rs:260-261`); 0065's `offices` list is an array of agent names (`docs/decisions/0065-capabilities-are-the-realms-to-grant.md:131`, where `review-security` is the agent file `agents/review-security.json`); and 0075 ruling 5's `provisional_offices` reads the same list, whose schema is `contracts/realms.v7.schema.json:5` and whose reader is `crates/brokkr-runtime/src/bundle/tier.rs:1-3`.

0021 ruling 1's list (`chief`, `review`, `security review`, `verify`, `ship`) is a different fact: the position a site occupies in a body, and whether a later site rules on its findings. This draft calls that fact a **gate role**, and keeps `office` for the agent's name. The two are bound, not merged:

- A site's role is structural, derived from its `SiteKey` (`crates/brokkr-runtime/src/bundle/site_key.rs:75-207`: single body, panel member, sequence step, sequence-panel member), the seat (`review`, `verify`, `ship`) and its position in the sequence. It is never read from the recipe's panel member key, the charter or a free step name.
- **The recommended answer to ask (g) is option g2: the grant names the hired office explicitly, and the structural role it may hold.** The office is the agent's name; the role is the structural position. A site matches a grant only when both equal the grant's. A security review lane is therefore a grant naming the office `review-security` and the role `review`; no non-test code string-compares an agent's file name to decide a role, and an operator's own agent needs its own explicit grant entry. A `security` slot hiring `review-correctness` is role `review` and does not match a grant naming `review-security`; a `correctness` slot hiring `review-security` is the `review-security` office at role `review`, and matches only the grant that names that office.
- `chief` is structural: the last step of a `review` sequence, when that step is a single gate-class site (a named agent or an inline command) and at least one earlier step exists. This rule takes precedence over the office for that site. That is the work-panel-then-chief shape the controller runs (`recipes/gpt-flash/bundle.json:89-113`: a work-class `positions` panel, then a gate-class `chief`) and the gate-panel-then-chief shape. A panel member keyed `chief` inside a one-step panel is not a chief: it rules on no other step, and it is a `review` site. A gate-class step before the last is role `review`, not chief.
- A `verify` or `ship` seat has no grantable role today: `agents/verify-reviewer.json` and `agents/release-manager.json` declare no `access`, and 0098 ruling 3 reads an absent access as writes, so no shipped office can hold either role. They are outside the grant until an office declares read-only; that is a later decision, not a role variant this one adds with no consumer (0071 ruling 6).
- An inline site, and a site with no hired agent, has no office and therefore no role. A grant never applies; where such a site's model matches a grant, the compile refuses it explicitly (`GrantNoOffice`) rather than guessing an office or a role.
- Every other gate site has no role, so a grant never applies and 0021 ruling 2 and 0041 ruling 3 stand.

Ask (g) asks the operator to rule this vocabulary; the recommended option is g2, which names both words and removes the office-name inference.

## The trust subjects, named separately

A gate's verdict passes through six subjects. They are not interchangeable, and today's compile reads only two of them.

| # | Subject | What it decides | Where it lives today | The gap |
|---|---|---|---|---|
| i | The harness: its code and plugins, at a release | Whether the prompt and the verdict are carried faithfully; whether the harness's own tools and ambient configuration are off | The adapter's measured `mcp.shapes` and `hands` fragment (`adapters/dsh.json:60-162`); the composed-tree check and its measured 99 rows (`docs/decisions/0098-a-dsh-hands-seat-runs-on-its-composed-tree.md:40-58`; `docs/evidence/adapters/dsh-hands-round2.md:9-39`); 0075 ruling 3's probe (`docs/decisions/0075-harness-onboarding-in-a-day.md:116-129`) | `trust_tier` is one line for every release. The one-way check below proves every release the adapter's cold boxed shape names is in the driver's set, which is what an admitted grant depends on; it does not prove the reverse. |
| ii | The harness's own native capabilities, apart from the route's provider network | Whether the harness can reach a network or a process outside the box through a tool of its own: native web fetch, native web search, a native shell, subagents | The adapter's `native_capabilities` inventory (`adapters/dsh.json:157-158`); 0065 ruling 4's per-capability ON/OFF declaration (`docs/decisions/0065-capabilities-are-the-realms-to-grant.md:159-166`); 0075 ruling 4's refusal where no OFF is measured (`docs/decisions/0075-harness-onboarding-in-a-day.md:137-140`) | The inventory is adapter-wide, and dsh declares it `unmeasured`. | iv | The abstract model | Whether the model's judgment has been measured and is allowed to hold a gate | 0041 ruling 3's `judges` (`crates/brokkr-runtime/src/agents.rs:437`); dsh declares none (`adapters/dsh.json:46`); 0075 ruling 5's `tier` (`crates/brokkr-runtime/src/agents/load/models.rs:24-65`) | The list is adapter-wide and all-or-nothing; dsh's empty list refuses every abstract model, and a name added to it would admit that model on every route. A bare model id reads promoted, so an absent tier cannot distinguish a grandfathered model from a new preview. |
| v | The office and the gate role it holds | Which office is hired and which structural gate it occupies: the role is `review` (grantable) or `chief` (never granted) | 0021 ruling 1's class, carried at the site as `class: gate`; 0041 ruling 2's roster (`docs/decisions/0041-one-office-per-seat.md:154-199`); the site's structural identity, `SiteKey` (`crates/brokkr-runtime/src/bundle/site_key.rs:75-207`); the hired agent's `office` (`crates/brokkr-runtime/src/capabilities.rs:260-261`) | A gate is one bit. Deriving the role from the recipe's member key is wrong (the key is recipe data, and a recipe cannot grant); deriving it from the agent's name alone is the new precedent the review rejected. The six travel together. Today's `judge_link` reads the tier and the judges; it does not read the release, the route, the native inventory, the office and role, or the box, except to let a boxed `exec` pass. That is the right fail-closed default for an untrusted driver, and it is why a work-class panel member under a trusted chief is lawful today: the member is not the gate. A scoped grant adds the missing subjects one named exception at a time, and keeps the default for everything it does not name.

## The options

### (A) It stays impossible

The documented pattern is the work-class panel member under a trusted chief. The guidance says: an untrusted route may contribute findings to a panel; it may not be the panel's chief, a standalone review gate, a security gate, verify, ship, or any other gate. Do not build a second adapter to get around it; the reasons are option E's.

**Consequences.** The refusal stays exactly as 0021 ruling 2 writes it, with no new data, refusal, digest or readout. The downstream security lane keeps a dsh member and a trusted chief; the untrusted model never holds the verdict. The cost is that a model the operator judges qualified still cannot be the check, and the only road to that is a full tier promotion of dsh (0021 ruling 3), which trusts every route and model — exactly the blanket the issue refuses. Option A also leaves the second-adapter workaround as the only apparent way, so it needs the guidance and, if ask (e) is taken, a compile refusal to make the guidance real.

**Residual to name.** The work member still sends the worktree to DashScope, under 0036's egress class and 0065's capability grants; the chief still reads the member's findings, which may be wrong or prompt-injected. Those are the accepted costs of an advisory member, not a gate.

### (B) A scoped gate grant

The operator rules, with an evidence line (0021 ruling 3), that one (adapter, route, abstract model, concrete model id, office) may hold the named gate role, and only when every condition below holds. The ruling lives where rulings live, as a dated addendum to this decision once it is accepted; the adapter data enacts it, as 0021 ruling 2 enacts a tier and 0075 ruling 6 enacts a promotion.

The conditions, all of them:

1. **The adapter is still untrusted, and the grant is not a tier.** `trust_tier` stays `untrusted`; `judges` stays empty; the grant is a separate list. The adapter is trusted for nothing else, on any route or model. A grant on an adapter already `Trusted` is a load refusal: a tier is the broader grant, and a scoped exception beside it would misstate which one admitted the seat.
2. **The route, the abstract model, the concrete id and the hired office are named exactly.** The grant names a route, an abstract model, a concrete id and the office (the hired agent's name). At load, the route must be the concrete id's route segment under 0036 ruling 2: split the id once at the first `/` (the same split `resolve_route` reads, never a string prefix) and require the first segment to equal the grant's route. A grant naming `dash` does not reach `dashscope/qwen3.8-max`. The abstract model must be in `models`; at compile, `models[model]` must equal the grant's `concrete` exactly, or the grant refuses and names both ids. The route need not be declared in `routes`; if it is not, its class is `uncontracted`, and that class governs the route's own network to its provider, which is outside the box by design (`crates/brokkr-protocol/src/hands.rs:4-10`); the grant names the class and does not change it. A grant on a route whose class is `local` is a load refusal (`GateGrantLocal`), because 0036 ruling 3 says local confers no gate seat; the downstream case is DashScope, not Spark. A grant that has moved to another route or model refuses the same way, with both ids named.
3. **The model is explicitly promoted, never provisional.** The downstream Qwen Max preview is a new model, and 0075 ruling 5 starts a new model provisional. The adapter must write `tier: provisional` until 0075 ruling 6 promotes it; the compile reads the written tier (`crates/brokkr-runtime/src/agents/load/models.rs:24-65`) and the existing provisional gate refusal stops a provisional model before the grant is read (`crates/brokkr-runtime/src/bundle/tier.rs:78-89`). For a grant, absence is not enough: 0075 ruling 5's binding names `tier: provisional | promoted`, and 0107a makes the loader accept the written `promoted` word and records the declared tier once, as `Adapter.tiers: BTreeMap<String, ModelTier>` with `ModelTier::{Provisional, Promoted}`. That one map carries the three states — absent (legacy, reads promoted for every ordinary seat but cannot carry a grant), provisional, promoted — so the grant's requirement is not a second set beside the provisional one. The per-model tier lives in that map, and the replacement sentence in [0075 ruling 5](#0075-ruling-5s-ruling-stands-its-binding-sentence-changes) names the location, so 0075 ruling 5's "an adapter or route field" is not read as a contradiction. An adapter that leaves the tier out still reads promoted for every ordinary seat, but it cannot carry a grant, so a bare `qwen-max` cannot become a gate by the accident of an absent field. Promotion is 0075 ruling 6's wager and roster addendum, not this grant. The grant and the promotion are two rulings; both are needed, and the grant's evidence line cites the promotion.
4. **The office is named, the role is structural, and the grant is never a chief.** The grant names one hired office (the agent's name, `crates/brokkr-runtime/src/capabilities.rs:260-261`) and one gate role. A site matches the grant only when both equal it. The role is derived from the site's `SiteKey` — the compiler's one structural identity: the seat, the selected case and the body path (`crates/brokkr-runtime/src/bundle/site_key.rs:75-207`) — and never from the recipe's panel member key, the charter, a free step name or the agent's file name. One table:
    - a single `review` seat, or a panel member of a `review` seat, is role `review`; the office is whatever agent is hired there, and a grant must name it;
    - the last step of a `review` sequence, when that step is a single gate-class site (a named agent or an inline command) and at least one earlier step exists, is role `chief`, whatever body that single site wraps (a work-class panel followed by a gate-class chief, `recipes/gpt-flash/bundle.json:89-113`, and a gate-class panel followed by a chief are both this shape). This rule takes precedence over the office for that site. A panel member keyed `chief` inside a one-step panel is not a chief: it rules on no other step, and it is role `review`. A gate-class step before the last is role `review`, not chief;
    - a `verify` or `ship` seat has no grantable role today, because no shipped office declares `read-only` access for it (0098 ruling 3); it is not a grant role until an office exists;
    - an inline site and a site with no hired agent have no office and no role; a grant never applies, and a model match is refused with `GrantNoOffice`;
    - every other gate site has no role, so a grant never applies and 0021 ruling 2 and 0041 ruling 3 stand. The clarify and analyze judges are such seats (`recipes/triage/bundle.json:84-90`, `:137-141`).

    The grant's `role` is the closed enum `review | chief`. `chief` is a known word so the loader can refuse it with the operator's text (`GateGrantChief`) instead of "unknown role"; a grant may not contain it. The word `security-review` is not a grant role: 0021 ruling 1 calls the position "security review", and the security intent is carried by the office `review-security` (`agents/review-security.json`), which the operator names in the grant. The grant never names `chief`; ask (b) asks the operator to confirm that, and ask (f) asks whether a sole-check non-chief role may be named. The compile refuses a `chief` role even when the site's agent office appears in another grant, because the structural table, not the name alone, decides the role.
5. **The seat is boxed with workspace hands, on a measured release and host, with the office's declared read-only access, a read-only worktree bind and measured binds.** The site declares hands; the realm's boundary is `namespace`, `seatbelt` or `container` (0046 ruling 4), and the boundary is the realm's, not the recipe's (0046 ruling 1). The hands declare `network: false`; the hired office's declared `access` is `read-only` (0098 ruling 3); the site's whole hands spec — kind, network and binds — must digest to the value the grant names. Every explicit bind is `ro` or `overlay`; an `rw` bind is refused (`GrantBindMode`), because a grant is a read-only office and `rw` writes land on the host (0043 ruling 2). The worktree bind itself must be `ro`: the `workspace` call's implicit read-write worktree bind (`crates/brokkr-protocol/src/hands.rs:10-14`) does not satisfy the grant, and 0098 ruling 3's read-only worktree bind is a prerequisite. Until that bind is built and part of the resolved hands spec and digest, every grant refuses (`GrantWorktreeBind`). The grant names a release, and the compile requires the adapter's **cold, boxed** measured shape on that release and the boundary's host: `native_write`, `store_read`, `process_read` and `ambient` must all be `Measured` (`crates/brokkr-runtime/src/agents/mcp.rs:167-174`; 0075 ruling 3). The replacement boxed shape re-measures none of the ten hands rows (`adapters/dsh.json:133-154`) and does not qualify; the cold boxed shape is the one measured (`adapters/dsh.json:111-131`). A `seatbelt` boundary needs a macOS shape, and the adapter has only a Linux one, so a grant is admitted under `namespace` on Linux until a macOS shape is measured; `container` has no measured shape and is refused. The adapter's `hands.harness` is not a substitute: dsh declares none, and 0046 ruling 4 refuses it at a `harness` gate (`docs/decisions/0046-the-boundary-is-named.md:179-185`). A `network: true` box is refused (`GrantNetwork`): the box bounds a `workspace` call and nothing else (`hands.rs:4-10`), so its own network off is a workspace control, not the harness's egress control; the harness's own native egress is condition 6's subject.
6. **Every native capability that can reach outside the box is measured OFF for the granted release, or granted to the office by the realm.** The route's own network to its provider is outside the box by design (`crates/brokkr-protocol/src/hands.rs:4-10`) and is governed by 0036's egress class for the named route (condition 2); the grant does not change it. Every other native capability the harness can use to reach a network or a process outside the box — native web fetch, native web search, a native shell, subagents — must be measured OFF by the adapter's declared disabling control (0065 ruling 4's declaration, the probe's measurement under 0075 ruling 4) for the exact release the grant names. Where the realm instead grants that capability to that office under 0065, the realm's grant is the only other way, and the 0107 grant does not stand in for it. The compile reads the adapter's native inventory for the grant's release: an `unmeasured` inventory is refused (`GrantNativeEgress`), and so is a declared capability whose OFF control is not measured on that release and that the realm does not grant to the office; the refusal names the capability (or the unmeasured inventory), the adapter and the release. `adapters/dsh.json:157-158` declares dsh's native capabilities unmeasured, so today no grant on dsh can compile; 1052a's measurement (or a later one) must record the OFF controls for its release before a dsh grant is admitted.
7. **Every fallback link qualifies on its own.** A fallback link passes by the trusted tier and `judges`, or by its own grant; it never inherits an earlier link's grant. A link that follows a granted link and is itself untrusted and ungranted is refused at that link by the existing `refuse_untrusted_gate`, naming it; there is no separate grant refusal for a link without its own grant (0071 ruling 5). This is 0041 ruling 3's "on any link" read at compile time, and it is already how `judge_link` is called per link (`crates/brokkr-runtime/src/bundle.rs:2410-2445`). A trusted-judge fallback is not refused by this condition.
8. **No secret-binding and no egress grant is implied.** The grant does not raise `egress_minimum`, does not stand in for 0021 ruling 4's binding grant, and does not grant a 0065 capability. The existing `refuse_secret_egress` still runs on the link (`crates/brokkr-runtime/src/bundle/route_policy.rs:99-167`), and a boxed site with secret bindings is refused by 0043 ruling 2's enforcement binding (`docs/decisions/0043-the-hands-are-one-tool.md:113-116`). A gate may hold an `egress` capability only where the realm names that office explicitly (0065 ruling 7); a 0107 grant is not that naming. The route's class, and the realm's capability map, are read and reported, not changed.
9. **The grant does not weaken the judge check for any other model.** A link with no matching grant still faces `refuse_untrusted_gate` and `refuse_unjudged_model` in their present order. A link that matches a grant on its abstract model and concrete id is judged by the grant, and a matching grant that misses any condition is refused with that condition named, never silently fallen back to the tier refusal. An inline site has no agent and no office; a grant never applies to it, and it faces the tier and judges as today. Where an inline or office-less site's model matches a grant, the compile refuses it with `GrantNoOffice`, naming the missing office, rather than guessing one.

**Compile refuses everything else and names the missing condition.** The refusals are in `route_policy.rs`, one variant per condition, with the operator's text preserved and the decision's condition numbers cited. The exact messages are sketched in [Enforcement binding](#enforcement-binding-named-not-built).

**Consequences.** The downstream case can have a dsh Qwen Max security review gate, but only boxed, read-only, with a read-only worktree bind (0098 ruling 3, still owed), on a measured release and host, with the measured binds, an explicitly promoted model, a named non-chief role and office, every native capability measured OFF or realm-granted, every fallback qualified, and no secret or egress grant. The operator records the evidence once, in the ruling; the adapter carries the data; the compile refuses the rest. New data moves the adapter and bundle digests; no wire contract changes. The cost is a new adapter list, a new compile path, a new doctor readout, a new run-start carrier, and a new thing to get wrong. The benefit is that the exception names exactly what it admits, and the blanket workaround is unnecessary. Two consequences follow from today's tree, not from the design: the dsh adapter declares its native capabilities unmeasured (`adapters/dsh.json:157-158`), so no grant on dsh can compile until 1052a's measurement (or a later one) records the OFF controls for its release; and the read-only worktree bind is not built, so no grant compiles at all until 0098 ruling 3 lands.

**Residuals to name.** A harness compromised between measurements; a provider that changes the model behind the same concrete id; a route's profile base URL re-pointed at another endpoint; a grant that outlives its evidence; a box that is measured on one host and runs on another; a native capability the harness gains after its release was measured; and the read-only worktree bind 0098 ruling 3 still owes. The recommendation below names each and what this decision does and does not do about it.

### (C) Adapter-wide trust for dsh

Set `"trust_tier": "trusted"` on `adapters/dsh.json`, and add the model to `judges`. The gate passes.

**Consequences.** One line trusts the binary for every route: the local Spark, DashScope in Singapore, the OpenRouter routes, the DeepSeek official route, and every route the operator adds tomorrow. A route re-pointed to a new provider inherits the trust without a ruling. The `judges` list is adapter-wide, so every model in it is admitted on every route, including a model that a future adapter update marks provisional (0075 ruling 5 still refuses that one, but the grant's scope is wrong even where it is refused). It breaks 0021 ruling 7's symmetry: codex earned `trusted` by a wager recorded in the ledger (`docs/decisions/0021-model-policy.md:97-110`); dsh would get it by one edit for one route. It collapses 0036's three-destination table into one answer, which is the mistake 0036 was written to end. The compile cannot tell an operator's deliberate trust from a workaround. Rejected.

### (D) A per-route trust tier

Add a trust tier to the `routes` map, so `dashscope: trusted` while `spark: untrusted`. This follows 0036's unit and is narrower than C.

**Consequences.** It is still model-blind, role-blind and office-blind: every model on `dashscope` — Qwen Max, GLM, DeepSeek, and any future alias — would hold every gate its agent is seated at, including a provisional model unless the provisional check also runs. It moves the judging axis into 0036's egress map, which is exactly the braid 0021's context untangles; 0036 ruling 3's "local grants no gate seat, no trust tier" would have to be read around a new field on the same map. It also gives a route-wide exception with no box, release, access, binds or model condition. It is a legitimate fallback if the operator wants a route-wide grant, but it is not the scoped grant the issue asks for. Not recommended.

### (E) A second trusted adapter

The workaround, named: a second adapter file over the same `dsh` driver, `trust_tier: trusted`, with the model in `judges`, seated at the gate, and the abstract model renamed because the loader refuses a name mapped twice (`crates/brokkr-runtime/src/agents/load.rs:649-663`).

**Consequences.** It is C in another file: the driver is trusted for every route and model. It duplicates the models map, routes, credentials and tool grammar, and it gives one driver two provider identities in the manifest, the doctor and the journal. A route added to the real adapter and not the copy is judged by a stale map; a route added to the copy and not the real one silently inherits trust. 0036 rejected one adapter per route for the duplication (`docs/decisions/0036-egress-is-a-property-of-the-route.md:63-66`); this is worse, because the copy also carries a different trust tier, and the renamed model strands every agent that hired the original name. Rejected. Ask (e) asks whether the compile should refuse the same-driver, different-tier shape so the guidance is not the only guard.

## The recommendation

**B is the ruled road. A is the answer until B is built.**

Against A alone: A is safe, and it is what the tree does today, but it answers the ask with "no" and leaves the downstream case with a work member forever. It also leaves the second-adapter workaround as the only way to get the model into a gate, which is the outcome the issue exists to prevent. A is the right interim because B and its prerequisite measurements (1052a's native OFF controls and 0098 ruling 3's read-only worktree bind) are not built; it is not the right final answer for an operator who is willing to record the evidence B asks for.

Against C: C is the blanket the issue refuses. It trusts three jurisdictions, every model and every future route for one route's evidence. The adapter is the right unit for a tier; it is the wrong unit for this exception.

Against D and E: D is narrower than C but still model-blind, role-blind, box-blind and release-blind; E is C with duplication and a renamed model. B is the only option that names the route, the model, the concrete id, the office and the role, and that requires the release, the host, the office's declared read-only access, the read-only worktree bind, the native OFF controls and the binds, refusing each one it does not get.

Why B is lawful within the existing decisions, rather than beside them:

- 0021 ruling 2 gives the tier as the broad grant and the compile refusal as its enforcement; B is a named exception, recorded by the operator, and the amendment below writes it into that ruling rather than around it.
- 0021 ruling 3's road is evidence then an operator ruling. B uses that road for a route and a model instead of a driver; it does not create a second kind of evidence.
- 0021 ruling 4 keeps egress separate; B consumes the separation instead of merging it.
- 0021 ruling 5's no-substitution rule is a run-time park; B's per-link compile rule is 0041 ruling 3's "on any link", and it substitutes nothing.
- 0021 ruling 7 keeps newcomers symmetric; B is the same road for a newcomer, scoped, and a newcomer still starts with no gate.
- 0036's route is B's scope, not B's authority. `local` still confers nothing (0036 ruling 3), and a local route refuses a grant (`GateGrantLocal`), so that ruling stands unamended.
- 0041 ruling 3's `judges` stays the adapter-wide list; B is a separate list, and a grant is never written into `judges`.
- 0075 ruling 5's "never a gate" is untouched: the existing provisional gate refusal stops a provisional model before the grant is read. 0075 ruling 6's wager is the promotion B requires, and B adds the written `promoted` word its binding already names.
- 0043 ruling 3's boxed `exec` is the precedent that the box changes what a gate's trust has to cover; B borrows the box, not the exemption. A model has a stochastic axis, so the box is necessary but not sufficient; the promotion evidence and the native OFF measurement are the other two halves.
- 0046 ruling 4 already names the boundaries that may hold a gate; B requires one of them and refuses `harness` and `open`.
- 0065 ruling 3 keeps the realm the only granter of capabilities; B grants none and leaves the realm's map in force. 0065 ruling 4 is B's native-egress condition: a native capability that cannot be switched off is refused unless the realm grants it to the office.

**The residual risks, named.**

1. **A harness compromised between measurements.** The release pin and the probe are point-in-time. A different installed release is refused at run start by the exact-match carrier (condition 5), but a binary or plugin replaced under the same version is not detected, and a supply-chain compromise can carry the prompt or the verdict. This decision does not solve that; it requires the measured release, makes doctor re-read the installed version, and leaves the binary's own integrity to the operator's install and the host's package controls. A future decision could pin the harness binary by digest; that is out of this story.
2. **A route re-pointed at another model, or another endpoint.** The grant pins the concrete id, and the compile refuses an alias that no longer maps to it. But a provider can change the weights or the model behind the same published id; the concrete id is not a digest. Separately, the route name is adapter data, but the endpoint — dsh's profile base URL — is not: a profile edit can re-point `dashscope` at another host with every pinned fact unmoved (the measured evidence records the endpoint it saw, `docs/decisions/0036-egress-is-a-property-of-the-route.md:36-38`). The grant's evidence line names the endpoint and the date; any change to the id re-opens the grant, a change behind the id does not, and a profile re-point is caught only by re-reading the profile. Doctor can print the route's declared credential and class, not the profile's endpoint. The wager's run ids are the evidence, and a re-wager is the remedy.
3. **A grant outliving its evidence.** The grant is bound to the measured release, the concrete id and the hands digest. Any of those changing re-opens it; the compile refuses a release the adapter no longer measures with the axes it measured, and a concrete id the alias no longer maps to. A grant whose evidence is stale but whose facts have not moved is not caught by a fact check; ask (c) asks for a typed review date, and the recommendation is a recorded review, not a hard expiry.
4. **A box measured on one host and run on another.** 0098 closes the boxed dsh hands shape on Linux; macOS keeps a residual (`docs/decisions/0098-a-dsh-hands-seat-runs-on-its-composed-tree.md:3-5`). A grant used on macOS before the seatbelt measurement is not covered by the Linux evidence; the compile requires a measured shape on the boundary's host (condition 5), and doctor names the host the evidence stands on.
5. **The role derivation.** The grant names the office and a structural role; the compile maps the site through `SiteKey` and compares the hired office. A `security` slot hiring `review-correctness` is role `review` at office `review-correctness`, and a grant naming `review-security` refuses; a `correctness` slot hiring `review-security` is the `review-security` office at role `review`, and a grant naming `review-correctness` refuses; a single `review` seat and a panel member are both `review`. A non-final gate step of a `review` sequence is role `review`, not chief, and is served; a gate step with no earlier site and no later chief is a sole check, which ask (f) rules. A custom agent needs its own grant entry. A new gate agent with no role is refused rather than guessed. The residual is that `review` covers a single review seat and a panel member alike; ask (f) is where the operator rules whether a sole check may be named at all.
6. **The read-only worktree bind is a prerequisite, not a residual.** 0098 ruling 3 says a read-only `HandsSpec` "does not exist in this round … the read-only hands bind stays owed" (`docs/decisions/0098-a-dsh-hands-seat-runs-on-its-composed-tree.md:73-79`). A granted `read-only` office stands on dsh's `sandbox-policy` row, the box's `ro` and `overlay` binds, and the box itself; the worktree stays read-write inside the box until that bind is built. Condition 5 therefore refuses every grant (`GrantWorktreeBind`) until 0098 ruling 3's read-only bind is part of the resolved hands spec and digest. The operator should not read the grant's `read-only` word as a read-only worktree until that slice lands, and 0107b's slice plan names it as a predecessor.
7. **A native capability the harness gains after measurement.** The inventory is measured on the grant's release, and a capability the harness adds later is not in that measurement. The release pin and the typed inventory check are the controls; a harness that changes its native surface under the same release is not detected. This is the same point-in-time limit as risk 1, read on the egress axis, and doctor names the release the inventory was measured on.
8. **The boxed `exec` exemption is not widened or narrowed here.** 0043 ruling 3 admits a deterministic command at a gate because its blast radius is the box (`docs/decisions/0043-the-hands-are-one-tool.md:118-124`). A script that wraps a model is not a deterministic command, but the compile cannot tell one from the other; that pre-existing path is unchanged by this decision and is named as a follow-up, not fixed here.

Until B and its prerequisites (1052a's native OFF measurement and 0098 ruling 3's read-only worktree bind) land, the operator should use A: the dsh model as a work-class panel member, with a trusted chief. The operator should not seat a dsh gate on the strength of this proposal alone.

## The asks for the operator

Each ask is a choice with a recommended option, and each is unruled. The operator can rule each in one line; the "Ruling line" is the sentence to accept or replace.

### (a) Where the grant lives

**Option a1 — the adapter, as a new `gate_grants` list beside `routes` and `judges`.** Recommended. The route, the abstract model, the concrete id, the office and the measured release are adapter facts; 0036 put the route class there, 0041 put `judges` there, and 0075 put the model tier there. One file, one digest, one operator edit. The list is not nested inside `routes`, because `routes` is a map from a route name to an `EgressClass` (0036 ruling 2) and a grant is not a class. A recipe cannot write it: the adapter library is the operator's data, and a recipe may not grant (0065 ruling 3). The cost is that a personal or per-realm variation has no supported home today: 0101 is accepted but unbuilt (`docs/decisions/0101-personal-realms-and-adapters-live-outside-the-tracked-tree.md:6`), and its ruling 4 keeps no personal adapter root in this build (`:158`, `:670`, `:735`). A variation therefore needs its own adapter in the tracked tree, or waits for 0101.

**Option a2 — the realm, per role, beside `capabilities`.** The realm is already the only granter of capabilities (0065 ruling 3), and 0046 makes the boundary a realm fact. A realm entry could name the adapter, route, model, office and role. The cost is that the realm would restate adapter data it does not own: the route's concrete id and the measured release live in the adapter, and a realm that names them can drift from it. A hybrid — the adapter names the route, model, office and release; the realm names the role — is the strongest form of a2, but it splits one grant across two files and makes the compile read two sources for one fact.

**Recommended: a1.** It keeps 0036's route data, 0041's judges and 0075's tier in one operator file, and the realm keeps the capability and boundary facts that are already its own.

**Ruling line:** `0107(a): the grant lives in the adapter, as a gate_grants list beside routes and judges.`

### (b) Whether a grant may name the review chief

**Recommended: no.** The chief is the seat that rules on the other gate seats' findings and absorbs their errors; its failure compounds every member's error, and it is the last word on the panel's verdict. A model that is not trusted adapter-wide should not be that seat, and a chief on an untrusted route would make the panel's advisory pattern impossible to reason about. The chief stays a trusted adapter's judge (0041 ruling 3). A later wager may promote the route for the chief role; that is a new operator ruling expanding this grant's role, not a use of the present grant, and it is not available in this decision. The compile refuses a grant that names `chief`, and refuses a `chief` role even if a grant lists its agent office. This ask does **not** decide the standalone non-chief roles; ask (f) does.

**Alternative, not recommended:** allow the chief. It would let the downstream case replace its trusted chief, but it would also make the untrusted route the final word on every finding in the panel, and it would collapse the distinction between an advisory member and the check. The residual risk is exactly the one 0021's context names: "gate seats ARE the check, and nobody stands behind the judges" (`docs/decisions/0021-model-policy.md:16-22`).

**Ruling line:** `0107(b): no; a grant names no chief role.`

### (c) Whether a grant expires, or is re-proved when the harness release, the route's target model or the hands composition changes

**Option c1 — bound to the facts it names, no clock.** Recommended. The grant is bound to three facts it names: the measured release, the concrete model id and the hands digest. The compile checks the box, the boundary, the office's declared access, each bind's mode and the native OFF controls against the site and the adapter; those are compile checks, not fields of the grant. The compile refuses a release the adapter no longer measures with every isolation axis measured, a concrete id the alias no longer maps to, a host the adapter has no shape on, a hands digest that does not match, a bind mode that is not `ro` or `overlay`, and a native inventory not measured OFF on the granted release. Any change to one of the three named facts re-opens the grant; the operator records a new evidence line. This is stronger than a calendar against a changed release, because the dangerous change is effective immediately, not at the expiry date.

**Option c2 — a calendar expiry, in 0025's manner.** 0025 ruling 2 makes an expiry mandatory for Skírnir's operator-signed grant, "a grant without one is invalid" (`docs/decisions/0025-skirnir.md:43-51`). A grant that expires after a stated period, and is re-proved at expiry, catches a grant whose facts have not moved but whose evidence is old. The cost is that a stale grant stays live until its date, and a release can change the day after it is signed. 0025's shape is cited only for the expiry idea; its grant is a different grant, for the standing executor (#476), and its signature and ceiling are not imported here.

**Recommended: c1, with a typed review date.** The grant is invalidated by any change to the three facts it names. Its `review_by` field is a typed date, parsed at load and printed by `brokkr doctor`; a missed review date does not keep a changed fact admitted, and the date is a recorded prompt, not a hard expiry by itself. If the operator prefers a hard expiry as well, c2's date can be added without changing c1.

**Ruling line:** `0107(c): bound to the measured release, the concrete model id and the hands digest; any change re-opens it, with a typed review date.`

### (d) The evidence bar

**Option d1 — the full bar.** Recommended:
- the wager under 0075 ruling 6 on real stories, comparing the route and model with the incumbent on cost per accepted change (#224) and on review holds and rounds (#436), with its run ids. The stories seat the model work-class, under a trusted chief (option A's shape), in the office the role requires — for the security lane, the `review-security` office at a `review` site — so the evidence can be produced before the grant exists: the compile refuses the model at the gate until the grant, and the wager runs as a work seat under the chief;
- the conformance probe's report for the harness release (0075 ruling 3), with the version, host, date and evidence;
- the hands composition measurement (#896 for the measured releases; 1052a for `0.2.2-rc.1`), on the route and concrete model the grant names where the shape can be scoped to it, or on the shape the adapter measures where it cannot: the composed tree's measured rows, one `dsh-mcp-client` and Brokkr's workspace tool, the harness's own tools off, the box, the office's declared read-only access, the read-only worktree bind, and every bind's mode (`ro` and `overlay` only). The read-only worktree bind 0098 ruling 3 owes is a grant condition, so the evidence line names the slice that built it or says the grant is refused;
- the native capability measurement (0065 ruling 4; 0075 ruling 4): for every native capability the harness can use to reach a network or a process outside the box, the declared OFF control and the release it was measured on, or the realm's grant of that capability to the office. The route's own network is the named route's egress class, not a native capability;
- the route's declared egress class and jurisdiction (0036), named, and the endpoint the measurement saw; the grant is not an egress grant;
- the operator's evidence line, recorded in the ruling as 0021 ruling 3 requires, and the promotion as 0075 ruling 6's roster addendum.

**Option d2 — the probe and hands measurement, without a wager.** Cheaper, and enough to show the harness can run boxed; not enough to show the model's judgment is worth a gate. A preview model with no wager is exactly the case 0075 ruling 5 keeps provisional; d2 would let a model into a gate on a harness measurement alone.

**Option d3 — the operator's judgment alone, with a stated reason.** The law's floor is an operator ruling with an evidence line (0021 ruling 3); a ruling with no evidence line is not one. Not recommended.

**Recommended: d1.** The wager is what makes the model's judgment a measured claim rather than an impression; the probe, the hands measurement and the native OFF measurement are what make the harness and the box measured. The wager story is work-class under a trusted chief, so asking for it does not require the grant it is evidence for.

**What the compile can and cannot enforce.** The compile enforces every measurable precondition: the explicit promotion, the concrete id, the office and role, the box, the boundary's host, the office's declared access, the read-only worktree bind, the hands digest and its bind modes, the release's cold boxed shape, each of its measured axes, and the native inventory's OFF controls for the release. It cannot read a wager, a probe report or an operator ruling, and the `evidence` string is a pointer for doctor and for the ruling's record, not a proof. A grant with a measurable precondition missing is refused by the compile for the missing data; the wager, the probe report, the hands measurement, the native measurement and the operator's evidence line are the operator's ruling, and d1's bar is that ruling's authority, not a compile check.

**Ruling line:** `0107(d): the full bar — wager on real stories, probe report, hands composition on the named route and model, native OFF controls for the release, egress class and endpoint named, operator evidence line.`

### (e) Whether compile should refuse the second-adapter workaround

**Option e1 — refuse two adapters that name the same driver at different tiers.** Recommended. `Adapters::load` refuses the pair by name, with both files and both tiers, before any gate is judged. Where the adapter's `driver` argv is a `{brokkr} driver <kind>` dispatch (`adapters/dsh.json:22-26`), the key is the **driver kind** — the token after `{brokkr} driver`. Where it is not a `brokkr` driver dispatch (`crates/brokkr-runtime/src/bundle.rs:2434`: "the command is no driver dispatch"), the key is the canonicalised argv itself, with the `binary`, so the same direct command at two tiers is refused the same way. `binary` alone is never the key: it is only what doctor probes, and the shipped data already differs (`adapters/lanetally.json:27-35`: binary `claude-lanetally`, driver `lanetally`). A check on `binary` is passed by any other string. A repository can still copy the driver under another kind, but that is a new built-in driver — code, not data — visibly not the same adapter, and the guidance says not to. The check closes the exact workaround the issue names and makes the compile's refusal a property of the tree, not a convention.

**Option e2 — guidance alone.** Simpler, no false positives, and no new refusal. But the workaround is invisible: the second adapter passes every existing check except the duplicate-model one, which it sidesteps by renaming, and the only record is a second file. The issue's downstream has already found it; guidance that the compile does not enforce is the weaker answer.

**Recommended: e1.** The refusal is a name check, not a proof; it cannot see a copy or a wrapper, and the residual is named in the consequences. It does not need a new contract: the adapter files are library data, and the refusal is a load error naming both files.

**Ruling line:** `0107(e): yes; compile refuses two adapters naming the same driver (or, for a non-dispatch argv, the same command line) at different tiers, naming both files.`

### (f) Whether a grant reaches a sole-check role

Ask (b) excludes the chief because the chief rules on other gate seats' findings. It does not decide whether a grant may name a **sole-check** non-chief role — a single `review` site, or a `review` panel that no later gate step rules on — where the granted model's verdict (or the panel's) is the check and no trusted chief stands behind it. The compile can tell this structurally from the same `SiteKey` and body walk: a gate site with no later gate step ruling on it is a sole check. `verify` and `ship` are outside this ask until an office declares read-only for them.

**Option f1 — yes, the grant names the office and the role it admits, sole-check or panel member.** Recommended. The evidence conditions are the same and the office and role are named (condition 4); a sole-check role is exactly where d1's wager in that office matters most. The chief is special because it rules on other seats, not merely because it is last, and its exclusion is a separate ruling (ask (b)). The compile applies the same box, release, host, access, binds, worktree bind, native OFF and fallback conditions, so a sole-check grant is no broader than its role.

**Option f2 — no, a grant is confined to a gate-class panel member that a trusted chief rules on.** This is the shape that is lawful today (option A) moved from work to gate. It is narrower and keeps a trusted model behind every granted verdict; the cost is that a standalone security lane, or a review panel with no chief, cannot use the grant, and the downstream case must be a panel member with a trusted chief. If the operator wants that narrower answer, the enforcement binding drops every `review` site that is a sole check (a single review, or the last gate step with no chief after it), and a "sole check" refusal names the structural reason.

**Recommended: f1.** The grant is role-scoped and the evidence bar is per office and role; refusing a sole-check role would leave the downstream case unserved whenever it is not a panel member, which is the ask's own case.

**Ruling line:** `0107(f): yes; a grant may name a sole-check non-chief role, with the same conditions.`

### (g) What the word for the structural gate position is, and whether the grant names the office

The tree already uses `office` for the hired agent's name (`crates/brokkr-runtime/src/bundle/tier.rs:9`; `crates/brokkr-runtime/src/capabilities.rs:260-261`), and 0065's `offices` and 0075's `provisional_offices` read that name (`contracts/realms.v7.schema.json:5`; `crates/brokkr-runtime/src/bundle/tier.rs:1-3`). 0021 ruling 1's `chief`, `review`, `security review`, `verify`, `ship` are a different fact: the site's structural position. The operator should choose the word and the field, so the same word does not carry two meanings in one realm.

**Option g1 — keep `office` for the agent's name, and name the structural fact a `gate role`, but do not name the office in the grant.** The grant's `role` decides alone, so a `review` grant covers every review office on that route and model. Simpler, but it cannot distinguish a security lane from a correctness one, and it is the role-wide blanket that the name-based inference was trying to avoid.

**Option g2 — bind both words in the grant: name the hired `office` and the structural `role`, and require both to match.** Recommended. A grant entry carries `office: "review-security"` and `role: "review"`, and a site must match both. No non-test code string-compares an agent's file name; the operator names the office explicitly, and an operator's own agent needs its own entry. The cost is a second field, and a custom agent or an operator's own agent needs an explicit entry before it can be admitted. It also removes the hard-coded `review-security` inference the review rejected, and it makes a `security` slot hiring `review-correctness` miss a grant naming `review-security` exactly as it should.

**Option g3 — keep the structural sense as `office` and rename the agent-name sense.** This is the issue's prose, but it would rewrite 0065, 0075, `SiteAsks.office` and `tier.rs`'s own sentence; it is out of 0107's scope and would be a separate semantic change.

**Recommended: g2.** It names both facts in the grant, removes the new precedent of deciding a role by an agent's file name, and leaves every existing `office` sentence true. The grant's role enum is `review | chief`; `chief` is refused, and `verify`/`ship` are not grantable until an office declares read-only.

**Ruling line:** `0107(g): bind both words in the grant — the grant names the hired office and the structural gate role, and a site must match both.`

### The data fields

A new top-level `gate_grants` list on the adapter, beside `routes` and `judges` (`crates/brokkr-runtime/src/agents.rs:396-437`), and the loader's `ADAPTER_KEYS` gains `gate_grants` (`crates/brokkr-runtime/src/agents/load.rs:707-728`):

```json
"gate_grants": [
  {
    "route": "dashscope",
    "model": "qwen-max",
    "concrete": "dashscope/qwen3.8-max",
    "office": "review-security",
    "role": "review",
    "release": "0.2.2-rc.1",
    "hands": "sha256:<the canonical hands spec's digest>",
    "review_by": "2027-02-11",
    "evidence": "#1052, 1052a, the promotion addendum and the wager run ids"
  }
]
```

There is no `access` field: the grant has no access of its own, and the compile reads the hired office's declared `read-only` (0098 ruling 3). The example's release is the one 1052a measures; today the adapter measures only `0.2.1-rc.2`, so a `0.2.2-rc.1` grant is refused until 1052a writes that shape. The example is refused today for two further reasons that conditions 5 and 6 give: the read-only worktree bind is not built, and dsh's native inventory is unmeasured.

The typed shape, in a new `crates/brokkr-runtime/src/agents/load/gate_grant.rs`:

- `GateGrant { route: String, model: String, concrete: String, office: String, role: GateRole, release: String, hands: HandsDigest, review_by: time::Date, evidence: String }`, parsed once at the edge with `deny_unknown_fields` (0071 ruling 3). An absent `gate_grants` is the empty list, so every adapter on disk reads exactly as it does today.
- `GateRole` is a closed enum with `Review` and `Chief`, written `review` and `chief`. `Chief` is a known word so the loader can refuse it with the operator's text (`GateGrantChief`) instead of "unknown role"; a grant may not contain it. The `verify` and `ship` words are not grant roles until an office declares read-only for them, so they are unknown words today, not variants with no consumer (0071 ruling 6).
- `HandsDigest` is a newtype, not a raw `String`: it parses `sha256:` followed by 64 lowercase hex, and its parse failure names the canonicalisation. The bytes are `brokkr_core::canonical::sha256_hex(HandsSpec::to_value())` for the site's resolved hands (`crates/brokkr-protocol/src/hands.rs:148-217`), the same canonical value the manifest pins (`crates/brokkr-runtime/src/bundle.rs:4228-4236`); no untyped string reaches the check.
- `review_by` is a `time::Date` parsed from `YYYY-MM-DD` at load, not a free-text date inside `evidence`; doctor prints it, and a past date is a readout, never a refusal.
- `Adapter` gains `tiers: BTreeMap<String, ModelTier>`, with `ModelTier::{Provisional, Promoted}`, replacing the existing `provisional: BTreeSet<String>`. The three states are one typed fact: absent (legacy, reads promoted for every ordinary seat and cannot carry a grant), `Provisional`, and `Promoted`. The existing provisional check reads `ModelTier::Provisional`, and the grant check requires `ModelTier::Promoted`.
- `route`, `model`, `concrete`, `office`, `release` and `evidence` are non-empty. A repeated entry — the same route, concrete id and office granted twice — is a load refusal naming the adapter and the grant. A route that is not the concrete id's `<route>` segment (split at the first `/`), a model not in `models`, a local route, a grant on a `Trusted` adapter, or a `chief` role is a load refusal naming the adapter and the entry.
- A grant is a load refusal on a driver kind with no exact-release carrier (`GrantNoCarrier`), naming the driver and the adapter. `dsh` is the one carrier today; `adapters/lanetally.json` writes no `trust_tier`, reads untrusted, and carries no pin, so a grant there is refused.
- Two adapters that name the same driver — the kind for a `{brokkr} driver <kind>` argv, the canonicalised argv with the binary otherwise — at different `trust_tier`s are a load refusal naming both files and both tiers (ask (e)'s e1).
- The grant is part of the adapter's bytes, so it is digested with the adapter and moves every bundle that pins it. It is not a wire contract and mints no contract version.
- The `evidence` string is a pointer for doctor and for the ruling's record, not a proof; the compile cannot read a ruling, and the operator's recorded ruling is the authority 0021 ruling 3 requires. It is non-empty by load, so doctor has no "missing" state for it.

The native check reads the adapter's existing `native_capabilities` inventory (`crates/brokkr-runtime/src/capabilities.rs:609-636`) and the realm's capability grants, not a new field: an `unmeasured` inventory is the refusal's whole case, and a `known` inventory's OFF control is measured for the grant's release when its typed `release` (added beside the OFF entry by 0107b, whose `native_capabilities` schema gains it) equals the grant's. The realm's grant for the capability to that office is the only other admission.

### The one rule, and the refusals

A gate link passes when one of these holds: it is a boxed `exec` (0043 ruling 3, unchanged); or its adapter is `Trusted` and its abstract model is in `judges` (0021 ruling 2; 0041 ruling 3, unchanged); or one or more grants name its abstract model, concrete id and route, and the grant whose office and role the site matches admits it with every condition holding. A grant is looked up by abstract model, concrete id and route; the site's hired office and derived role then select among the grants that share that key. If grants share the key at different offices, the site selects its own; if none names its office and role, `GrantRole` refuses, naming the site's office and role and the grant that shares the key. A model and concrete id with no grant at all is a no-grant link. The grant is judged in this order:

1. **`GrantConcrete`:** the resolved concrete id must equal the grant's `concrete`; a moved alias or route names both ids.
2. **`GrantPromotion`:** the model must read `ModelTier::Promoted` in the adapter's `tiers`; a bare or absent tier names 0075 ruling 6.
3. **`GrantNoOffice`:** the site must hire an office; an inline site or a site with no agent has none, and a grant never guesses one.
4. **`GrantRole`:** the site's hired office and derived role must equal the grant's `office` and `role`, and the role is never `chief`.
5. **`GrantUnboxed`:** the site must declare hands and the realm's boundary must be `namespace`, `seatbelt` or `container`.
6. **`GrantNetwork`:** the hands must declare `network: false`.
7. **`GrantAccess`:** the hired office's declared access must be `read-only`.
8. **`GrantBindMode`:** every explicit bind must be `ro` or `overlay`; an `rw` bind is refused.
9. **`GrantWorktreeBind`:** the worktree must be bound read-only by 0098 ruling 3's read-only hands spec; the implicit read-write bind refuses until that slice lands.
10. **`GrantBinds`:** the site's whole hands spec, the read-only worktree bind included, must digest to the grant's `hands`.
11. **`GrantHost`:** the boundary's host must have a measured shape; `namespace` is Linux, `seatbelt` is macOS, `container` has none.
12. **`GrantRelease`:** the adapter must have a cold boxed shape at the grant's `release` on that host.
13. **`GrantAxes`:** that shape's `native_write`, `store_read`, `process_read` and `ambient` must all be `Measured`, and the refusal names the first that is not.
14. **`GrantNativeEgress`:** for each native capability the adapter declares, the realm must grant it to the office, or its OFF control must be measured on the grant's `release`; an `unmeasured` inventory is refused whole. The refusal names the capability (or the unmeasured inventory), the adapter and the release.

A link with **no matching grant** is a separate state. If it is trusted and its model is in `judges`, it passes. If it is trusted and misses `judges`, the existing `refuse_unjudged_model` refuses it and names the link. If it is untrusted, the existing `refuse_untrusted_gate` refuses it, unchanged; there is no separate grant refusal for a link without its own grant (0071 ruling 5).

A link that matches a grant and misses a condition is refused with that condition named; it does not fall back to the tier refusal. `refuse_secret_egress` runs on every link after the gate check, unchanged, and a grant never bypasses it.

The messages, one per variant, in the operator's text:

- `GrantConcrete`: "seat '{what}' gate link {link} seats model '{model}' as '{actual}', and the grant names '{granted}'; a grant is bound to the concrete model id, and a re-pointed alias or route re-opens it (decision 0107 condition 2)."
- `GrantPromotion`: "seat '{what}' gate link {link} seats model '{model}', whose adapter '{adapter}' does not write `tier: promoted`; a grant requires the 0075 ruling 6 promotion to be written on the model, not inferred from an absent tier (decision 0107 condition 3; decision 0075 ruling 5)."
- `GrantNoOffice`: "seat '{what}' gate link {link} has no hired office; a scoped gate grant names the office it admits, and an inline site or a site with no agent has none (decision 0107 condition 4)."
- `GrantRole`: "seat '{what}' gate link {link} hires office '{office}' at the {role} role, which the grant for route '{route}' and model '{model}' does not name; a grant names one office and one role, and never the chief (decision 0107 condition 4, ask (b))."
- `GrantUnboxed`: "seat '{what}' gate link {link} is not boxed with workspace hands (boundary '{boundary}', hands {presence}); a scoped gate grant holds only a boxed workspace-hands seat under namespace, seatbelt or container (decision 0107 condition 5; decision 0046 ruling 4)."
- `GrantNetwork`: "seat '{what}' gate link {link} declares hands with network on; the grant requires a no-network box for the workspace call, which is not the control for the harness's own egress (decision 0107 condition 5; decision 0075 ruling 4)."
- `GrantAccess`: "seat '{what}' gate link {link} hires office '{office}', whose declared access is '{access}'; the grant requires 'read-only', because the measured hands rows and the store mask stand on a read-only office (decision 0107 condition 5; decision 0098 ruling 3)."
- `GrantBindMode`: "seat '{what}' gate link {link} binds '{path}' as '{mode}'; a scoped gate grant admits only 'ro' and 'overlay' binds, because 'rw' writes land on the host (decision 0107 condition 5; decision 0043 ruling 2)."
- `GrantWorktreeBind`: "seat '{what}' gate link {link} runs with the worktree bound read-write; a scoped gate grant requires a read-only worktree bind, and the read-only hands bind decision 0098 ruling 3 owes is not built (decision 0107 condition 5; decision 0098 ruling 3)."
- `GrantBinds`: "seat '{what}' gate link {link} seats hands digest '{actual}', and the grant names '{granted}'; a grant is bound to the measured box, the read-only worktree bind included (decision 0107 condition 5)."
- `GrantHost`: "seat '{what}' gate link {link} runs under boundary '{boundary}', whose measured host is {host}, and adapter '{adapter}' has no cold boxed shape there; it measures {measured} (decision 0107 condition 5; decision 0046 ruling 4)."
- `GrantRelease`: "seat '{what}' gate link {link} names release '{granted}', and adapter '{adapter}' has no cold boxed shape at that release; it measures {versions} (decision 0107 condition 5; decision 0075 ruling 3)."
- `GrantAxes`: "seat '{what}' gate link {link} names release '{release}', whose cold boxed shape records {axis} as {state}; the grant requires every isolation axis measured (decision 0107 condition 5; decision 0075 ruling 3)."
- `GrantNativeEgress`: "seat '{what}' gate link {link} names release '{release}', and adapter '{adapter}' declares {capability} without an OFF control measured on that release, or declares its native capabilities unmeasured; a grant requires every native capability that can reach outside the box to be measured OFF for the release, or granted to the office by the realm (decision 0107 condition 6; decision 0065 ruling 4; decision 0075 ruling 4)."

The load refusals (`LibraryError`, naming the adapter and the entry): a grant naming `chief`; a grant on a `Trusted` adapter; a route that is not the concrete id's `<route>` segment; a local route; a model not in `models`; an empty field; an invalid `review_by`; an unknown role; the same route, concrete id and office granted twice; a grant on a driver with no release carrier; and two adapters naming one driver at different tiers. `GateGrantChief` names ask (b); `GateGrantTrusted` names condition 1; `GateGrantConcrete` names 0036 ruling 2; `GateGrantLocal` names 0036 ruling 3; `GrantNoCarrier` names condition 5's carrier sentence; the duplicate-names refusal names 0071 ruling 5.

### The slices

The former 0107a is split so that no slice admits a grant before its release pin and its read-only worktree bind exist, and so that the over-ceiling files (`bundle.rs`, `agents.rs`, `load.rs`, `doctor.rs`, `model_policy_tests.rs`) do not grow. The role derivation, the per-link state and the tests live in new modules; a call site in an over-ceiling file is a one-line delegation, offset by moving the block it replaces into the new module, so the ratchet's net count does not rise. The `Adapter` fields are carried by a small nested value whose type and doc text live in the new modules, and the slice moves the `Adapter` paragraph they replace into those modules, so their net line count does not rise either; if the ratchet still refuses a file, the slice returns oversized rather than raising the baseline.

**The predecessor — 0098 ruling 3's read-only worktree bind.** This is not a 0107 slice; it is the slice 0107b depends on. `crates/brokkr-protocol/src/hands.rs` gains the read-only worktree bind, and the resolved `HandsSpec` and its digest include it. ## Consequences

- **What changes for a bundle that uses no grant:** nothing. An adapter without `gate_grants` loads as today; the tier and judges path is unchanged; the digests of every current bundle do not move.
- **What changes for a bundle that uses one:** the adapter's bytes and the bundle's identity move; the compile reads one more list and one more model fact; the driver reads one more carrier; the doctor prints one more section. A grant is visible in the manifest through the adapter digest, and its refusals name the condition.
- **What does not change:** `trust_tier` and `judges` keep their meanings; 0036's egress map and classes; 0043's box and its hands-and-secrets refusal; 0046's boundary; 0065's capability grants; 0075's provisional tier and promotion road; the wire protocol. No contract version is minted. No adapter, recipe or realm is edited in this story.
- **What it costs:** one more adapter list, one more compile path, one more run-start carrier, one more doctor readout, and one more thing for the operator to keep true. The grant's evidence is a point-in-time measurement, and the residual risks above are the price of admitting a model that the blanket tier would have admitted for the wrong reason.
- **What is refused until its prerequisites land:** today's dsh adapter declares its native capabilities unmeasured (`adapters/dsh.json:157-158`), so `GrantNativeEgress` refuses every dsh grant until 1052a's measurement (or a later one) records the OFF controls for its release; and the read-only worktree bind is not built, so `GrantWorktreeBind` refuses every grant until 0098 ruling 3 lands. Both are named in the slices, not left to the reader.
