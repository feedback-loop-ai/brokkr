## Architecture and actual authority

This is a close control-plane peer to Brokkr: Python owns story progression while fresh coding CLI sessions perform implementation and review. The typed transition table permits `PENDING → DEV_RUNNING → DEV_VERIFY`, then review, commit, deferral or escalation; illegal transitions raise `IllegalTransition`. `COMMITTING` can end in `DONE`, `ESCALATED`, or `AWAITING_OPERATOR`. That last outcome commits verified work while retaining human-only external actions; confirmation is a later operation rather than an agent claiming those actions occurred. The transition table is small, but the surrounding engine, verification and recovery code is extensive. [State machine](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/src/bmad_loop/statemachine.py), [engine](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/src/bmad_loop/engine.py).

The effective flow is: load BMAD story/spec inputs and local TOML policy → validate tools and configuration → select a story → spawn a stage-specific CLI adapter → observe hooks/artifacts and bound execution → verify the resulting repository/spec → optionally run independent review → commit or preserve/defer/escalate. Sprint-board and typed `stories.yaml` modes share the delivery loop. Worktree isolation, adapter profiles and plugins extend this fixed lifecycle; they do not make the outer scheduler an arbitrary workflow graph. Role instructions come from installed BMAD skills and profile-specific invocation conventions, rather than a general immutable charter interpreter. [Setup and entry composition](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/src/bmad_loop/runsetup.py), [profiles](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/src/bmad_loop/adapters/profile.py), [stories orchestration](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/src/bmad_loop/stories_engine.py).

A consequential qualification to the earlier survey: `review.enabled=true` defaults to `trigger="recommended"`. The implementation skill always does its inline review; an additional session normally runs only if the skill sets `followup_review_recommended`. `trigger="always"` requests the separate second opinion for every story, while disabling review permits direct commit after development verification. Follow-up damping can converge and refile a lingering recommendation after its grant is exhausted. Thus deterministic routing exists, but mandatory independent review is a policy choice and can partly depend on an agent-authored recommendation. [Review policy](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/src/bmad_loop/policy.py#L211), [routing](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/src/bmad_loop/engine.py#L3100).

## Failure handling, lifecycle and recovery

Policy defaults bound development attempts to two, review cycles to three, sessions to 90 minutes, individual git operations to 120 seconds, and teardown grace to 20 seconds. Idle/stall nudges, token accounting, per-session budget enforcement and artifact-size limits are separate controls. The source explicitly distinguishes a hard wall-clock/session bound from budget sampling that depends on an adapter's available usage signal. A budget feature cannot be assumed effective for an adapter whose transcript parser offers no mid-session usage. Review timeouts can retry, defer immediately, or salvage finalized work only after deterministic verification; status contradictions default to escalation. [Limits and policy validation](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/src/bmad_loop/policy.py#L79), [generic adapter](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/src/bmad_loop/adapters/generic.py).

Teardown does more than kill a parent process. It snapshots pane roots and descendant identities while the window is alive, kills the multiplexer window, polls within a shared deadline, then terminates or force-kills confirmed survivors. Linux identities use `/proc` process start times; other platforms use psutil where available. Unknown identities are reported rather than blindly signalled, and reused PIDs are excluded. The code explicitly admits that a descendant detached before enumeration, or within the enumeration/kill window, may escape; backends without pane PIDs fall back to window termination. Setting teardown grace to zero deliberately restores the older best-effort behavior. This is a useful lifecycle design, not proof of universal child containment. [Teardown](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/src/bmad_loop/adapters/generic.py#L1560), [process host](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/src/bmad_loop/process_host.py).

Recovery preserves earlier attempt work in git refs and uses byte snapshots for story/spec material outside normal git visibility. It can refuse reset or restore when path authority, target identity, snapshot completeness, or preservation cannot be established. This matters for user changes and agent-created symlinks, not just crashed processes. Post-kill reconciliation may rescue a terminal artifact only after liveness checks, so a timeout is not automatically equivalent to lost work or completion. [Recovery flow](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/src/bmad_loop/recovery_flow.py), [adapter reconciliation tests](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/tests/test_generic_tmux.py#L2713).

Resume is deliberately mutable. The CLI reloads current policy, journals that it changed, warns on changes to the pinned host execution surface, then stamps the new snapshot/digest. A human running `resume` is treated as re-authorizing current configuration; no separate drift refusal flag is required. Automatic child sweep launch instead compares the launch digest held in memory and refuses changed host execution settings. Some scope fields remain launch-pinned. This is substantially different from rejecting resume whenever a recipe/dependency identity changes. [Resume implementation](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/src/bmad_loop/cli.py#L2975), [configuration digest composition](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/src/bmad_loop/runsetup.py).

## Permissions, effects and evidence

The orchestrator is not a sandbox. Bundled profiles include Claude bypass permissions, Codex `--dangerously-bypass-approvals-and-sandbox`, and Gemini YOLO mode. Git worktrees isolate ordinary working changes but do not restrict host access. Shell verification commands and declarative plugin hooks are execution authority; only plugins declaring in-process Python require the explicit enabled-name allowlist before import. This narrow plugin boundary should not be described as generally making dropped plugins non-executable. [Claude profile](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/src/bmad_loop/data/profiles/claude.toml), [Codex profile](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/src/bmad_loop/data/profiles/codex.toml), [plugin trust](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/src/bmad_loop/plugins/trust.py).

Evidence combines `state.json`, JSONL journal rows, session logs and bounded verifier streams. State writes use a lock and atomic replacement. Journal append heals an unterminated tail, and readers expose malformed lines as markers. The append implementation explicitly disclaims fsync and locking of its probe/append window: a concurrent torn write can still consume two records. State and journal are not one canonical transactional pure fold. Recovery latches reduce individual effect replay risks, but no general transaction spanning an agent's external side effect and the journal was established. Claims of exactly-once arbitrary effects would be unsupported. [Persistence and journal limitations](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/src/bmad_loop/journal.py).

## Validation, tests and maintenance

Tests directly cover identity-less descendants, reused PIDs, wedged windows, wall-clock versus monotonic timeout behavior, timeout artifact salvage, symlinked verifier directories, state-lock nesting, byte-hostile snapshots, interrupted preservation and refusal before unsafe restore. These are concrete executable test cases read in source; they were not run during this research. [Lifecycle tests](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/tests/test_generic_tmux.py#L442), [restore tests](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/tests/test_recovery_flow.py), [journal tests](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/tests/test_journal.py).

Packaging requires Python 3.11+, PyYAML and regex, plus platform/feature dependencies: psutil on Windows, Textual for the dashboard and httpx for OpenCode. The README's “core is pyyaml-only” quick-start comment is stale against `pyproject.toml`. CI defines Linux Python 3.11–3.14 tests, Windows boundary/full matrices, real multiplexer gates, lint and type checks; selected pure modules receive strict Pyright checking. Test breadth does not establish live-provider behavior, and the project's testing doctrine intentionally avoids paid provider execution. Very large engine/test modules and numerous adapter seams are a real maintenance surface worth measuring rather than equating feature count with simplicity. [Packaging](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/pyproject.toml), [CI](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/.github/workflows/ci.yml), [testing doctrine](https://github.com/bmad-code-org/bmad-loop/blob/87e5687f05717f5503b696974220cf2a91399664/docs/testing.md).

## Lessons and Brokkr experiments

The strongest transferable mechanisms are identity-aware teardown, verified salvage after termination, preservation before destructive recovery, and explicit operator-only completion. Brokkr #403/#431/#434 can use those as failure-case inventories. Run a future authorized experiment that forks a child, detaches it at several lifecycle points, writes a terminal result just before timeout, and mutates an ignored spec during recovery; compare both observed cleanup and honest uncertainty reporting. Separately compare recommendation-driven versus mandatory review, including a forged recommendation field and resumed policy drift. Brokkr's protected-review policy and pinned manifest promise different invariants, but its open enforcement/qualification issues must be resolved before treating them as demonstrated advantages.

## Evidence ledger and limits

Mechanisms established by source: typed transitions; validated bounded policy; real session adapters; PID-identity-aware teardown; preservation/refusal paths; mutable resume; separate state/journal persistence. Documentation claims: deterministic delivery, operator UX and broad runtime support. Unknown here: provider-level success rates, end-to-end platform parity, malicious same-user containment, and arbitrary external-effect deduplication.
