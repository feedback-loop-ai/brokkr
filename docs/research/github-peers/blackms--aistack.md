## Architecture and setup surface

This TypeScript/Node system combines a CLI, MCP tools, web APIs, agent identity/memory, provider integrations, review loops, workflow DSL, checkpoints, audit, guardrails and optional sandboxes. Node 20+ is declared; mandatory dependencies include native SQLite and bcrypt alongside provider SDKs, Zod, YAML and authentication libraries. Docker/E2B/Daytona and telemetry/vector integrations expand the optional operational surface. This is a broader service architecture than Brokkr's Rust phase engine. [Package](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/package.json), [agent execution](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/agents/spawner.ts), [Docker adapter](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/sandbox/docker.ts).

A concrete DSL execution path is: YAML/JSON → Zod validation/version check → mutable `WorkflowContext` → async-generator scheduler → `runStep` bridge → register an agent → provider chat → result/verdict extraction → context update. The scheduler supports sequential steps, conditionals, nested parallel blocks, bounded backward jumps on errors or rejection, and a total execution cap. Parallel blocks use `Promise.all` and forward a shared `AbortSignal` to cooperating hooks. This is an implemented workflow interpreter, not just prompt conventions. [Parser](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/workflows/dsl/parser.ts), [executor](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/workflows/dsl/executor.ts), [CLI bridge](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/cli/commands/workflow-dsl-runner.ts).

Agent definitions include reusable prompts and capabilities; portable `.aistack-agent` files add versioned identity metadata, memory snapshots, suggested models, prompt overrides and tool-whitelist fields. Zod rejects unexpected schema keys; compatible major versions are checked; optional integrity digests are verified on import, while older unsigned bundles remain accepted. Import requires the agent type to exist locally and allocates a fresh identity while preserving original identity as provenance. These are useful portability mechanics. They do not prove portable `tool_whitelist` is enforced by every execution path: the inspected spawner constructs provider messages from the registered definition's system prompt and exposes no whitelist to `provider.chat`. [Portable schema](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/agents/portable-schema.ts), [import/export](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/agents/portable.ts), [spawner](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/agents/spawner.ts#L465).

## Concrete failures and mismatches between layers

Missing input references become empty strings. The resolver comment promises a console warning, but the inspected replacement branch returns `''` without one. Prototype/constructor traversal is explicitly blocked. Conditions use string operations rather than an embedded general evaluator; errors normally stop execution, but `on_error.fail_after=false` permits continuation. A `REJECT` without a configured rejection clause simply reaches normal progression. These semantics must be included when comparing with a protected-review contract. [Resolver and routing](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/workflows/dsl/executor.ts).

Several advertised controls stop at abstraction boundaries. The schema accepts per-step and default `timeout_ms`, but neither the DSL executor nor its CLI bridge reads these fields. The executor passes `signal`; the default CLI `runStep` destructures only `{agent, input}` and calls `executeAgent` without cancellation. Thus sibling-abort tests establish a cooperating hook contract, not production provider cancellation. The bridge also falls back to a successful-looking `[stub]` output if dynamic spawner/config imports fail, despite its comment saying it surfaces an error. These are direct source observations, not reproduced incidents. [Schema](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/workflows/dsl/schema.ts), [executor](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/workflows/dsl/executor.ts#L305), [bridge](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/cli/commands/workflow-dsl-runner.ts#L37).

`stopAgent` removes registry/database state, updates identity and emits evidence. It does not hold or signal an in-flight provider process. The review coordinator's `abort()` calls it and marks the loop aborted; the main review loop tests its iteration bound, without an explicit aborted-state condition before accepting a later provider result. Consequently abort-state persistence is not evidence that ongoing work is cancelled. CLI providers use promisified shell `exec` with a timeout and output buffer, but no inspected process-tree ownership protocol comparable to BMAD Loop's identity-aware reaping. Provider/model command interpolation also deserves a trust-boundary review before treating those configuration fields as hostile input. [Stop and execution](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/agents/spawner.ts#L283), [review loop](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/coordination/review-loop.ts#L350), [CLI providers](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/providers/cli-providers.ts).

## Governance and effects

The coder/adversarial coordinator enforces iteration limits and interprets explicit approve/reject output. Configured input guardrails run before coder execution; blocked output can prevent forwarding to the reviewer. Output-only observation mode logs failures without blocking. Unknown guardrail names and validation crashes are intended to fail closed; the runner converts crashes/timeouts into high-severity failures. Its fast-failure path deliberately allows other guardrails to finish in the background, so “kill switch” here means return a failed decision early, not terminate all validation activity. Persistence failures in the coordinator are logged and swallowed. [Review gates](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/coordination/review-loop.ts#L199), [guardrail runner](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/guardrails/runner.ts).

The Docker sandbox constructs argument vectors, pipes code on stdin, defaults to no networking/read-only root/non-root user, drops capabilities and caps memory/CPU/process count. It forwards only explicitly supplied environment variables. However this is an optional code-execution adapter, not evidence that all agents/providers are sandboxed. Timeout kills the Docker CLI; the comment relies on the daemon to reap its container, with no observed container-ID reconciliation in that path. Collected stdout/stderr strings are unbounded there. These are focused lifecycle/size questions for an experiment, not a claim that all container cleanup fails. [Sandbox](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/sandbox/docker.ts#L168), [sandbox tests](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/tests/unit/sandbox/security.test.ts).

## Audit and checkpoints: useful mechanisms, narrower guarantees

The audit chain uses canonicalized JSON, a domain-separated SHA-256 linkage, optional HMAC-SHA256, SQLite update/delete triggers, and an immediate transaction spanning last-hash read plus insertion. Payloads are bounded to 64 KiB in strict mode; configured field redaction is top-level only. These are real mechanisms closely overlapping Brokkr's evidence concerns. The public wrapper, however, disables audit after initialization failure and catches append failures without stopping the effect. Audit and application state live in separate connections/files, so there is no established atomic event/state transition or pure-fold runtime. [Chain](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/audit/chain.ts), [runtime wrapper](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/audit/index.ts).

The audit documentation's suggestion that any deletion becomes detectable is too broad. Verification walks available rows and checks hashes; without a separately trusted expected head/count, removal of a valid tail leaves a verifiable prefix, even with HMAC. An unsigned chain can be recomputed by a writer controlling the database. HMAC adds shared-secret authentication, not public attribution or correctness of events, and does not make missing emissions visible. These are limitations derived from the verification algorithm, not a compliance assessment. [Verification](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/audit/chain.ts#L322), [documentation claims](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/docs/AUDIT.md).

Checkpoints store JSON or gzip state rows by session/agent/step, enforce a decompression limit, and offer retention/read APIs. The `workflow resume` command merely loads and displays a checkpoint, then tells the user to rerun the original workflow; its implementation explicitly leaves reattachment to downstream executors. The DSL bridge does not wire its declared `defaults.session_id` into agent spawn, and no automatic hydration of that DSL context was found. A test named deterministic replay loads the same stored state twice; it does not rerun effects or a provider. Checkpoint presence therefore establishes durable snapshots, not deterministic end-to-end replay, exactly-once effects or tested crash continuation. [Checkpoint storage](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/persistence/checkpointer.ts), [resume command](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/src/cli/commands/workflow.ts#L170), [replay test](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/tests/unit/checkpointer.test.ts#L92).

## Test evidence and lessons for Brokkr

Tests inspect real SQLite chains for tamper detection, HMAC mismatch, trigger refusal and export/import; DSL tests cover prototype rejection, exact iteration bounds, loops, skipping and cooperative cancellation. CI defines Node 22 Ubuntu lint/typecheck/build/unit/integration gates, coverage on main and a 50-run consensus flake guard. The source review did not run these tests or independently verify published reliability claims. [Audit tests](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/tests/unit/audit-chain.test.ts), [DSL tests](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/tests/unit/workflows/dsl/executor.test.ts), [CI](https://github.com/blackms/aistack/blob/dda4ae3372bcbee37463f3ca876a2dd08f3f402d/.github/workflows/ci.yml).

The main lesson is to qualify the entire dispatcher chain, not only leaf utilities. Brokkr #429/#430/#433/#434 should trace timeout/cancellation/identity/budget values from schema through dispatch to the actual effect. Proposed authorized experiments: abort a parallel provider call; use a one-millisecond declared DSL timeout; crash between effect completion and checkpoint; remove an audit suffix; inject audit I/O failure; import a restrictive whitelist and observe the invoked tool surface. Record what stops, what only changes status, and what evidence is lost. aistack demonstrates that many attractive governance primitives can coexist while integration gaps remain decisive.
