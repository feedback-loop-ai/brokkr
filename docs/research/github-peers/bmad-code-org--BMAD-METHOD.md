## What is actually implemented

BMAD Method packages planning, architecture, implementation, review and specialist personas as skills consumed by a host coding assistant. The current repository is a Python tooling and skill tree, explicitly not a distributable Python package; each shipped script declares its own Python floor/dependencies through PEP 723. Installation uses a skills CLI or Claude/Codex marketplace, then a setup operation copies project runtime/configuration under `_bmad`. Node/npm and Git are prerequisites for the skills-CLI route; Python 3.11+ and `uv` support helper execution. Web bundles cover selected planning workflows. [README](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/README.md), [tooling configuration](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/pyproject.toml), [setup implementation](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad/scripts/setup.py).

The architecture is: installed skills and module manifests → project setup/configuration → default/team/personal customization merge → immutable rendered Markdown generation → assistant reads successive step files → plan/spec/artifact updates and helper commands → review/blocked/final status. “Sequential enforcement” in a workflow means an instruction to the assistant unless a separate helper checks that property. There is no demonstrated general scheduler that independently owns every transition, child process, or tool permission. BMAD Loop is a separate repository adding that execution layer. [Build workflow](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad-build/workflow.md), [unattended entry](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad-build-auto/SKILL.md).

The important correction to a shallow prompt-library characterization is the executable renderer. It loads Markdown sources, resolves customization/config values, renders with Jinja `StrictUndefined`, tracks `rendered()` cross-file links, rejects missing or omitted targets, and refuses undeclared persistent settings or unused invocation overrides. It performs an initial pass to discover consumed inputs, computes an identity from source hashes, resolved values, project/skill roots, renderer SHA-256 and Jinja version, then publishes a generation directory with output hashes. Reusing a generation verifies manifest equality and each listed file's hash. Staging plus rename handles competing publishers; malformed or corrupt generations are refused rather than overwritten. [Renderer](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad/scripts/render_skill.py#L475).

That snapshot establishes prompt/configuration provenance, with boundaries. Non-Markdown scripts/assets referred to by `{skill-root}` remain in the installed skill directory. Generation publication is not a signed artifact, an operating-system write protection, or a full transitive dependency lock; the assistant's execution tools and model are outside this manifest. The standard Jinja environment is not presented as a sandbox for hostile template authors. Re-entering a skill renders current installed/configured inputs; no universal refusal to resume under a new generation was established. [Identity and publication](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad/scripts/render_skill.py#L539), [renderer tests](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad/scripts/tests/test_render_skill.py).

## Agents, mandates and composition

The developer persona “Amelia” has responsibilities, identity, style, principles, persistent facts, activation extensions and a menu of skills. TOML layers merge defaults, team settings and personal settings; tables merge recursively, keyed array entries can replace matching IDs, and ordinary arrays append. Personas can carry across invoked skills. This offers reusable mandates and authoring ergonomics, but authority remains in editable instructions and the host assistant. On resolver failure other than a missing installation, the persona explicitly tells the assistant to merge the files itself, an intentional behavioral fallback that should not be mistaken for mechanically validated effective configuration. [Developer persona](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad-agent-dev/SKILL.md), [resolver](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad/scripts/resolve_customization.py).

Architecture skills maintain an “architecture spine”: stable decisions with Binds/Prevents/Rule fields, inherited parent invariants and deferred choices. A Python linter checks placeholder markers, duplicate/nonmonotonic decision IDs, missing fields and missing stack versions. It always returns exit code zero with findings in JSON; the reviewer/assistant decides whether the findings block handoff. This is a good division between mechanical checks and semantic review, but the linter alone is not an enforcement gate. [Architecture instructions](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad-architecture/SKILL.md), [linter](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad-architecture/scripts/lint_spine.py).

## Reviews, refusal and execution limits

`bmad-build-auto` represents one unattended iteration. The entry skill calls the renderer once and halts on rendering failure. Rendered instructions require blocking, collectively awaited subagents; unavailable subagents produce `blocked` with reason `no subagents`. This addresses a real host constraint: detached children cannot reliably resume an unattended assistant turn. It is a documented protocol, not a separate process supervisor. [Entry contract](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad-build-auto/SKILL.md), [HALT/subagent protocol](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad-build-auto/workflow.md).

The review step dispatches selected lenses, then classifies every finding with evidence and writes a triage row for each. An intent gap saves a patch and blocks; an invalid plan can loop back through implementation, but the persisted review counter blocks after five repair iterations. Patch verification failure also blocks. Prior unchanged findings can carry their verdict forward. Follow-up recommendations depend on the severity of patched findings and a named residual risk. Explicit review `none`, an empty lens instruction, and customized handoff commands are supported configuration surfaces. Thus independent review quality and mandatory review are separate questions. [Review mechanics](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad-build-auto/step-04-review.md), [customization](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad-build-auto/customize.toml).

Finalization instructions set `built` (or preserve `done` on an applicable follow-up), commit reviewed files when version control exists, check the working copy, and block if it remains dirty. HALT writes terminal status/reason to a plan or fallback artifact and optionally runs `on_complete`. Arbitrary handoff and completion instructions may invoke external tooling; no universal secrets broker, capability gate, timeout, process-group cancellation, or uncertain-effect reconciliation was established for those actions. Those responsibilities belong to the host/runtime or an outer orchestrator. [Finalization](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad-build-auto/step-04-review.md), [terminal protocol](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad-build-auto/workflow.md).

## State, graphs and recovery

The memlog script gives planning sessions append-style factual memory with attribution and configurable frontmatter. Each update reads the document, writes a temporary file, flushes/fsyncs, then atomically replaces it. It has no hash chain, signature, exclusive writer lock, or canonical event-fold runtime in the inspected implementation. Two concurrent appenders can race over the same old content and fixed temporary name; this is a source-derived limitation, not a reproduced failure. The memlog intentionally records terminal events as entries rather than carrying lifecycle status. [Memlog implementation](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad/scripts/memlog.py#L123), [memlog tests](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad/scripts/tests/test_memlog.py).

Ticket tooling supplies actual dependency processing: it resolves ticket/container references, checks cycles, computes ready/blocked groups and a remaining chain, and writes status to corresponding plan files. This is more than a prose workflow map, but readiness computation is not autonomous concurrent dispatch. Editable ticket and plan documents remain the persisted state. [Ticket implementation](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad-preview-ticketing/scripts/tickets.py).

## Tests, maintainability and Brokkr relevance

Renderer tests cover concurrent publication, corruption modes, source symlink escape, ambiguous config names, omitted references, changed renderer identity, changed Jinja version, invocation precedence and platform write refusal. Memlog tests cover ordering, attribution, scalar escaping and refusal to overwrite on initialization. Repository validation exercises the same manifest parser as setup, and pre-commit/CI includes strict file-reference and skill validation, manifest checks, Python tests, lint and documentation checks on Ubuntu and Windows. These tests demonstrate helper contracts, not assistant compliance with every instruction or production delivery success. [Rendering tests](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/skills/bmad/scripts/tests/test_render_skill.py), [manifest validator](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/tools/validate_manifests.py), [quality hooks](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/.pre-commit-config.yaml), [CI](https://github.com/bmad-code-org/BMAD-METHOD/blob/5e33d3c03ba53187a40ab679d5479cdd4b6ac2fb/.github/workflows/quality.yaml).

Brokkr should study the renderer's used-input identity, local override diagnostics, source-located failures, and immutable generation reuse. An authorized future experiment can change a referenced helper while retaining rendered Markdown, mutate a review override, and resume from a plan to identify exactly which changes each system notices. A second experiment should compare ticket-readiness checks with Brokkr's deliberately linear outer machine, without conflating a dependency graph with a scheduler. Brokkr's policy protection, pinned manifests and journal fold aim at stronger runtime invariants; its known dispatcher, policy-validation, restore and retry gaps still need qualification before asserting that advantage is realized everywhere.

## Evidence ledger

Source-established: executable snapshot compiler and tests; reusable layered personas; dependency-aware ticket helpers; atomic memlog replacement; deterministic artifact lints. Assistant-interpreted: workflow ordering, semantic verdicts, repair limit obedience, finalization and subagent coordination. Unestablished: enforced end-to-end process lifecycle, arbitrary effect deduplication, immutable authority across all referenced assets and host tools. The sibling [source manifest](source-manifest.json) contains exact source URLs, byte sizes and SHA-256 values with their inspected revision identifiers.
