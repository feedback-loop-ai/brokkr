## Architecture and supported use

Metaswarm distributes specialist agents, review rubrics, orchestration skills, project templates and shell/Node helpers across Claude Code, Codex CLI and Gemini CLI. The npm package is a cross-platform installer, requiring Node 18+; most orchestration is delivered as instructions to the selected host assistant. BEADS supplies task/dependency tracking, and GitHub CLI supports repository/PR operations. Actual external-tool adapters invoke Codex or Gemini. The older `ORCHESTRATION.md` is a relocation notice pointing to `skills/start/SKILL.md`, so treating that file as the current engine specification would miss the implementation. [Package](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/package.json), [orchestration relocation](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/ORCHESTRATION.md), [main skill](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/skills/start/SKILL.md).

The intended flow is: issue/intent → research and work-unit plan → multiple review lenses → approved dependency DAG → per-unit IMPLEMENT/VALIDATE/ADVERSARIAL REVIEW/COMMIT → BEADS closure and PR handling. Independent units can fan out; validation converges, reviewers fan out, and commits serialize. Task mode uses fresh coding subagents; team mode permits persistent coding teammates, while adversarial review always requires a fresh reviewer. The scheduler and its graph are largely assistant-interpreted: the repository does not establish a general executable outer transition engine with a canonical journal. [Four-phase orchestration](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/skills/orchestrated-execution/SKILL.md).

Role files provide substantial charter-like material: responsibilities, allowed tool descriptions, activation prerequisites, required inputs, output formats, failure rules and handoffs. The code-review agent distinguishes collaborative approval from binary adversarial spec compliance. The architect's concrete examples still contain assumptions from a TypeScript/Hono/Prisma/Clerk service architecture; users adopting the templates need to remove inappropriate project conventions rather than assume neutral universal guidance. These are reusable role instructions, not automatically enforced capabilities. [Code reviewer](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/agents/code-review-agent.md), [architect](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/agents/architect-agent.md).

## Review policy and recovery semantics

The four-phase skill requires the orchestrator to run verification itself, inspect file scope, enforce coverage thresholds and obtain a fresh adversarial PASS before committing. Every blocking finding causes reimplementation, full validation and another fresh review; three failed attempts trigger human escalation. Reviewers receive the spec/DoD/diff without the coder's self-assessment. Planned human checkpoints cover risky changes and external dependencies. This is strong procedural guidance for independent assessment, but the words “blocking state transitions” do not demonstrate a runtime that can prevent the assistant from skipping them. [Validation and gate rules](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/skills/orchestrated-execution/SKILL.md#L237).

Recovery persists the approved plan, project context, current work unit, phase and retry count in `.beads` Markdown files. The instructed recovery sequence reads them and runs `bd prime`; it then resumes from the described phase. The examples use ordinary overwrite commands, without a transactional event journal, expected revision checks, hash-linked evidence or a machine reconciliation protocol for “commit landed, state write lost.” This is valuable context recovery, but its guarantee differs from replaying Brokkr's canonical SQLite fold. [Persistence/recovery protocol](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/skills/orchestrated-execution/SKILL.md#L505).

Session hooks are actual executable support. Startup/resume/clear/compact and pre-compaction trigger a script that detects the host, avoids duplicate BEADS priming, emits structured context, and can run a setup helper to recreate missing mandatory files. That self-heal suppresses helper failure and continues. It improves onboarding continuity while also meaning session start may mutate local project instruction/configuration files. It does not validate that the restored execution-state prose matches actual repository effects. [Hook registration](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/hooks/hooks.json), [hook implementation](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/hooks/session-start.sh).

## External execution and concrete boundary gaps

The external-tools skill describes cost-aware fallback chains, retries, per-tool timeouts, independent validation, isolated worktrees and minimally exposed credentials. Its adapters do implement command validation, restricted temporary-directory modes, JSON output/logging and `env -i` with selected provider variables. Codex implementation uses `exec --full-auto -C <worktree>`; its reviewer uses `--sandbox read-only`. Gemini implementation instead uses `--yolo --include-directories`, while review uses `--sandbox`. The generic “minimal permissions” claim therefore needs runtime-specific qualification; passing HOME also leaves credential/config files accessible according to the CLI's own sandbox. [External-tool contract](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/skills/external-tools/SKILL.md), [Codex adapter](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/skills/external-tools/adapters/codex.sh), [Gemini adapter](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/skills/external-tools/adapters/gemini.sh).

`safe_invoke` uses coreutils timeout/gtimeout when available. Those invocations lack an explicit kill-after escalation; the macOS fallback signals a single recorded PID with TERM then KILL. No universal descendant identity, process-group ownership, post-kill liveness or detached-child reconciliation was established. Timeout/error classification is implemented; retry/fallback budgets are mostly directed by the calling skill. Secure temporary directories are removed on ordinary success/error paths, but the adapters inspected do not install a general signal/exit cleanup trap. [Common helpers](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/skills/external-tools/adapters/_common.sh#L92).

The inspected call ordering suggests a scope-check gap. Both implementation adapters stage and commit work before calling `verify_scope`. That helper checks `git diff --name-only HEAD`, so successfully committed out-of-scope changes disappear from its input. Its string-prefix check also accepts a sibling whose name starts with the allowed directory string, and untracked files are not covered by that diff before staging. Subsequent changed-file/diff-stat reporting likewise compares against the now-current HEAD. These are source-derived findings, not runtime reproductions. Suppressed git errors (`|| true`) further mean an adapter's zero provider exit is not proof that its commit or scope recovery succeeded. [Scope helper](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/skills/external-tools/adapters/_common.sh#L252), [post-provider commit ordering](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/skills/external-tools/adapters/codex.sh#L161), [Gemini commit ordering](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/skills/external-tools/adapters/gemini.sh#L178).

Evidence is a local JSONL external-tools log with timestamps, model/attempt/result fields and paths to raw output, plus git and BEADS/task material. Appending does not establish fsync, chain integrity, cross-file atomicity or provider-effect idempotency. Cost parsing returns zero when jq or expected output is missing, so a zero count can be unavailable evidence rather than free execution. A future comparator should make that unknown state explicit. [Logging and usage parsing](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/skills/external-tools/adapters/_common.sh#L573).

## Setup, validation and maintenance

The Codex shell installer follows mutable `main`, creates symlinked skills, and replaces its installation directory after a failed pull; it does not pin an immutable run dependency. Marketplace packaging is another path. Resource duplication across skill directories is managed by a Node synchronizer with hashes and a `--check` mode. That provides useful authoring discipline but is not run provenance. [Installer](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/.codex/install.sh), [resource synchronization](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/lib/sync-resources.js).

CI runs plugin/hook JSON validation, hook behavior tests, CI-template checks and resource synchronization on Ubuntu/Node 22. Additional tests exist for installer/platform/template handling, but the inspected CI does not run all of them and no external-adapter behavior suite was found in the test inventory. The hook tests exercise platform-specific setup nudges, deduplication and self-heal. CI-template “security tests” are text assertions that expected protections appear; they do not execute malicious inputs or establish semantic confinement. [CI](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/.github/workflows/ci.yml), [hook tests](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/tests/hooks/test-session-start.sh), [template tests](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/tests/templates/test-ci-template.sh).

There is an important inconsistency between templates. The CI coverage template validates the leading command, rejects shell metacharacters and invokes an argument array. The local pre-push hook instead evaluates the configured command with `eval`, suppresses typecheck/format failures, and runs broad `pkill -f` against test-runner names. Consequently “mandatory quality gates” vary by entry point and are not uniformly fail closed. [CI template](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/templates/ci.yml), [pre-push template](https://github.com/dsifry/metaswarm/blob/33d39f776f7fe29098dcf048955756a237e8cb40/templates/pre-push).

## Brokkr comparison and experiments

The best ideas are fresh review without coder framing, explicit DoD evidence, structured recovery context, planned checkpoints and synchronized reusable resources. They can improve Brokkr charters and qualification tasks without importing the whole framework. The highest-value authorized experiment would submit a change outside declared scope, force commit failure, interrupt after commit, and run a child that survives timeout; compare the claimed phase with repository/process reality. Also compare CI and local-gate failure behavior. Brokkr's fixed outer machine and protected review should make these invariants independently checkable, but known lifecycle/dispatcher/bounds/retry gaps mean that remains a qualification objective rather than an assumed win.
