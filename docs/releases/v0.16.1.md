# v0.16.1: `brokkr orders` joins as the fourteenth root, `forge.realms/v9` grants may name a tool dialect per provider, Antigravity CLI adds Claude 5.5 and `dsh` adds Qwen 4.0 Max as work models, a residual panel member's unreadable safety fact joins as unknown, and one `workspace` call may run an hour

v0.16.1 is a patch on [v0.16.0](v0.16.0.md). It includes everything
merged since
[v0.16.0](https://github.com/feedback-loop-ai/brokkr/releases/tag/v0.16.0)
(eleven commits).

It needs no manual migration: existing realm maps (`forge.realms/v1`
through `v8`) load unchanged, and opening an existing journal for
writing additively creates the work-order table and records
`orders_schema = 1` while leaving `database_schema` (1) and
`queue_schema` (6) unchanged. Read
[Upgrade and compatibility](#upgrade-and-compatibility) if you restore
backups with a 0.16.0 binary (`brokkr.journal-backup.v2`), route
`review-panel` residuals on safety facts, or depend on `brokkr-core`'s
`CapabilityGrant::dialect`, `GrantError` or `SCHEMAS` or match
`brokkr-store`'s `Damage` or `StoreError` exhaustively.

## What changed

### Work orders

- **`brokkr orders` joins as the fourteenth visible command-line root**
  ([#1272](https://github.com/feedback-loop-ai/brokkr/issues/1272),
  [#1327](https://github.com/feedback-loop-ai/brokkr/pull/1327); decision
  [0116](../decisions/0116-a-work-order-says-what-is-being-built-and-its-graph-feeds-the-queue.md)
  slice 1, accepted, amending decision 0113 ruling 1).
  - **The document and contract.** A work order is a typed Markdown
    document with a closed JSON header
    ([`contracts/work-order.v1.schema.json`](../../contracts/work-order.v1.schema.json)),
    rendered in canonical key order with single-line acceptance items.
    References are validated as HTTPS URLs against six shipped citation
    trackers (Azure DevOps, GitHub, GitLab, Jira, Linear and ZenHub) and
    optional adopter definitions under `.brokkr/trackers/` (for a found
    folder) or `./trackers/` (for a recipe library).
  - **The journal and verbs.** `brokkr orders` (defaulting to `list`,
    with `--json`), `show`, `add`, `edit` and `rule` store work-order
    events append-only in `work_order_events` (`orders_schema = 1`). A
    newly proposed or edited work order enters `proposed` (decision 0116
    ruling 10). `brokkr orders show WO-<n>` prints the text digest on its
    first line and renders invisible format characters visibly as
    `<U+XXXX>` marks (keeping `U+FE00` through `U+FE0F` intact);
    `brokkr orders rule WO-<n> --digest HEX --reason WHY` verifies that
    exact digest inside the transaction once every ask is closed
    ([read surfaces](../guides/read-surfaces.md#brokkr-orders--work-orders-and-their-citations)).
  - **Backup inventory v2.** `brokkr journal backup` now writes
    `brokkr.journal-backup.v2`, adding `schemas.orders` (or `null` when
    no marker is recorded); restore reads both `v1` and `v2` and verifies
    the v2 field against the snapshot (decision
    [0100](../decisions/0100-a-journals-backup-is-one-consistent-snapshot-with-a-versioned-inventory.md)'s
    accepted addendum of 2026-11-24).
  - **Not yet:** slices 2 to 4 of decision 0116 (queueing a work order,
    drawing the work-order graph and importing from trackers) are not in
    this release.

### Realms and capabilities

- **Under `forge.realms/v9`, one realm grant may name a tool dialect for
  each provider, and a seat holds only its own provider's**
  ([#1329](https://github.com/feedback-loop-ai/brokkr/issues/1329),
  [#1410](https://github.com/feedback-loop-ai/brokkr/pull/1410); decision
  [0126](../decisions/0126-one-realm-grant-may-name-a-tool-dialect-for-each-provider.md)
  rulings 1–5, accepted, amending decision
  [0065](../decisions/0065-capabilities-are-the-realms-to-grant.md)
  ruling 3).
  - **The contract and map grammar.**
    [`contracts/realms.v9.schema.json`](../../contracts/realms.v9.schema.json)
    adds a second grant form beside single-`dialect`: `dialects`, a
    non-empty map from provider name to tool dialect name under
    `dialects/tools/`, sharing `offices` and the `retain: false` veto
    across providers. A grant writes exactly one of `dialect` and
    `dialects`; writing both, neither, an empty map, an invalid provider
    or dialect name, or `tools` or any dialect restriction key beside
    `dialects` is refused at load with a typed `GrantError` naming the
    realm and capability. A per-provider grant does not narrow; a grant
    that must narrow stays a single-`dialect` grant.
  - **Validation and per-seat holding.** Every named dialect is judged
    as decision 0065 ruling 3 judges one (it must exist and serve the
    granted capability), and a provider-native dialect must sit under its
    own provider's key (`mcp` dialects may sit under any provider's key
    and are judged per seat as before). A seat holds only the dialect
    under its own provider's key with no fallback across keys: a
    provider with no key refuses `requires` and records a drop for
    `wants`, naming the providers the grant serves.
  - **Doctor and manifest pin.** `brokkr doctor` names each provider's
    dialect for a per-provider grant, and the run manifest's realms pin
    carries the v9 grant as written.
  - **Older maps stay untouched.** `forge.realms/v1` through `v8` stay
    frozen (`v8`'s bytes are pinned by digest) and load unchanged; under
    `v6` through `v8`, a key spelled `dialects` stays a dialect
    restriction key judged by the selected dialect's schema. Under `v9`,
    `dialects` is reserved by the engine, so a `v9` grant written with
    `dialect` reads as it does in `v8` only when it carries no `dialects`
    key; retagging a `v8` single-dialect grant that has a `dialects`
    restriction to `v9` fails with `GrantError::BothDialects`, while
    keeping the `v8` tag preserves its meaning.
  - **Not yet:** ruling 6 of decision 0126 (`0126b`, `#1329`) — the
    `dsh-native-fetch` and `dsh-native-search` dialects, `dsh`'s
    measured native inventory in `adapters/dsh.json`, overlay
    composition and moving Brokkr's own `realms.json` from `v6` to `v9`
    — is not in this release; Brokkr's shipped `realms.json` remains
    `forge.realms/v6`.

### Engine and review

- **A residual review-panel member's unreadable safety fact joins as
  unknown, never as safe** (decision
  [0120](../decisions/0120-a-review-panel-joins-a-residual-members-unreadable-safety-fact-as-unknown.md),
  accepted;
  [#1292](https://github.com/feedback-loop-ai/brokkr/pull/1292),
  amending decision
  [0008](../decisions/0008-second-wave-scope.md) ruling 3).
  - **Before:** `ReviewInputs::join` read a `residual` member's absent,
    `null` or mistyped `has_security_residual` as `false` and an
    out-of-vocabulary `max_residual_severity` as `none`, which could let
    an incomplete member satisfy a tracked-debt route.
  - **Now:** each fact is read typed or left `null` (which fails any
    `when` condition that reads it under decision 0004 ruling 4), while
    a witnessed `true` or a witnessed severity above `medium` from a
    sibling still dominates. An all-clean panel still writes `none` and
    `false`.
- **A review panel's scope and fixes flags are read as written, never
  defaulted** (decision
  [0121](../decisions/0121-a-review-panels-scope-and-fixes-flags-are-read-never-defaulted.md),
  accepted;
  [#1293](https://github.com/feedback-loop-ai/brokkr/pull/1293),
  amending decision
  [0008](../decisions/0008-second-wave-scope.md) ruling 3).
  - **Before:** the join wrote `fixes_applied: false` on every
    aggregate, whatever its members said, and read a `spec_defect` that
    was not a boolean as `false`.
  - **Now:** each member's `fixes_applied` and `spec_defect` is read as
    a boolean when it is one, as `false` when the member left it out,
    and as unknown otherwise. The joined flag is `true` when any member
    witnessed `true`, `false` when all read `false`, and `null`
    otherwise, which no `when` condition matches. No shipped recipe
    declares `fixes_applied`, and triage's `spec_defect` rules ask for
    `true`, so no shipped route changes.
- **One `workspace` call may ask for up to an hour** (decision
  [0123](../decisions/0123-one-workspace-call-may-run-an-hour.md),
  accepted;
  [#1291](https://github.com/feedback-loop-ai/brokkr/pull/1291)).
  - `timeoutMs` now admits `100` through `3,600,000` milliseconds (up
    from `600,000`, ten minutes). The `30,000` ms default is unchanged,
    the seat's `timeout_seconds` remains the outer session bound, and
    the tool's schema and description advertise the checked bound.
- **A contended step checkpoint keeps its stderr for the indeterminate**
  ([#1248](https://github.com/feedback-loop-ai/brokkr/issues/1248),
  [#1391](https://github.com/feedback-loop-ai/brokkr/pull/1391);
  decision [0012](../decisions/0012-sealed-secret-bindings.md)).
  - **Before:** when a peer's write lock outlasted a non-terminal step
    checkpoint's append patience, settlement cleared the active stderr
    before the lawful end, so `effect/indeterminate` carried only lock
    evidence and the masked tail was lost.
  - **Now:** the tail is retained under its attempt ID and restored by
    the lawful end before `effect/indeterminate`, naming the
    content-free stderr evidence and telling the masked tail after the
    park and run-lock release.

## Upgrade and compatibility

- **Migration and journal storage:** no manual migration is required.
  Existing realm maps (`forge.realms/v1` through `v8`) load unchanged
  and Brokkr's shipped `realms.json` remains `forge.realms/v6`.
  `database_schema` (1), `queue_schema` (6), `event_schema` (1),
  `driver_protocol` (1) and seat-record v8 are unchanged. Opening a
  journal for writing in 0.16.1 additively installs the
  `work_order_events` table (with its index and append-only triggers)
  and records `orders_schema = 1` in `meta`, without modifying existing
  runs, events or queue entries. As before, bundle digests cover the
  engine version (`0.16.1`), so a run started under `0.16.0` resumes
  only under a `0.16.0` binary.
- **Journal backups (`brokkr.journal-backup.v2`):** `brokkr journal
  backup` now writes `brokkr.journal-backup.v2` (`schemas.orders`).
  `0.16.1` restores both `brokkr.journal-backup.v1` and `v2`, whereas a
  `0.16.0` binary reads only `v1` and refuses a `v2` backup. Back up
  journals before upgrading if you may need to restore under `0.16.0`.
- **Command spellings:** nothing is renamed or removed. `brokkr orders`
  is added as a fourteenth visible root; all `0.16.0` spellings and the
  hidden `0.15` aliases (scheduled for removal in `0.17`, except
  `dispatch drive`) are unchanged.
- **Contracts:** `contracts/work-order.v1.schema.json` and
  `contracts/realms.v9.schema.json` are added beside the frozen
  contracts; no existing contract bytes changed. `forge.realms/v1`
  through `v8` stay frozen (`v8` becomes `reader` beside `v9` as
  `current`, with `v8`'s bytes pinned by digest) and every existing
  realm map loads unchanged. Retagging a `v8` map to `v9` has one
  exception, a single-dialect grant that also carries a `dialects`
  restriction key;
  [Realms and capabilities](#realms-and-capabilities) states it. The
  engine version moves from `0.16.0` to `0.16.1`.
- **Review panels:** when a `residual` panel member omits or mistypes
  `has_security_residual` or `max_residual_severity`, that joined fact
  becomes `null` rather than `false` or `none` (decision 0120; a
  sibling's witnessed `true` or severity above `medium` still
  dominates). Under decision 0004 ruling 4, `null` fails each `when`
  condition that reads that fact — per condition, not across the whole
  rule set — so a single `null` fact still lets any rule reading only
  the other fact match:
  - In `verify` and `preflight`, `REVIEW-RESIDUAL-ABOVE-MEDIUM` reads
    only `max_residual_severity` (`above: medium`) and
    `REVIEW-RESIDUAL-SECURITY` reads only `has_security_residual`
    (`true`), so a witnessed severity above `medium` still stops the run
    even when `has_security_residual` is `null`, and
    `has_security_residual: true` still stops it even when
    `max_residual_severity` is `null`; `REVIEW-RESIDUAL-NONE` reads only
    `max_residual_severity` (`at_most: none`, parking). Because
    `REVIEW-RESIDUAL-OK` (`done`) requires both
    `has_security_residual: false` and `max_residual_severity_above:
    none`, any `null` fact that does not match those earlier rules
    matches no route and parks unmatched instead of completing as
    tracked debt.
  - In `fast` (and overlays that inherit its residual rules, including
    `brokkr-fast`, `landing`, `panel-review` and `self`), every residual
    rule reads `max_residual_severity` (plus `visits_implement_gte` on
    exhaustion) and none reads `has_security_residual`: when
    `max_residual_severity` is `null`, no `fast` residual rule matches
    and the run parks unmatched (unless a `triage` overlay's
    `REVIEW-SPEC-DEFECT*` rule matches on `strategy_in` and
    `spec_defect: true`), whereas when only `has_security_residual` is
    `null`, a readable severity still routes on severity alone (for
    example, `info` or `low` still matches `REVIEW-RESIDUAL-OK` or
    `REVIEW-REFORGE-EXHAUSTED-DEBT` and ships as tracked debt, `medium`
    or higher still triggers `REVIEW-REFORGE` or its exhaustion
    stop/park rules, and `none` parks via `REVIEW-RESIDUAL-NONE`).
  - In the frozen production table (`policy/phase-machine.json`),
    `REVIEW-RESIDUAL-ABOVE-MEDIUM` still stops on a severity above
    `medium` even when `has_security_residual` is `null`, and
    `REVIEW-RESIDUAL-SECURITY` still stops on `has_security_residual:
    true` even when `max_residual_severity` is `null`; otherwise the
    unconditional `REVIEW-RESIDUAL-OK` fallback routes the `residual`
    (including with one or both facts `null`) to `regression`.
- **Review panel flags:** a table that reads `fixes_applied` or
  `spec_defect` from a `review-panel` aggregate now sees a member's
  witnessed `true` (`fixes_applied` was a constant `false` before), and
  `null` where a member wrote something that is not a boolean (decision
  0121). An absent flag still reads `false`. No shipped recipe's route
  changes; re-read a recipe of your own that declares either flag.
- **The crates' public API** (`quality/public-api/`):
  - **`brokkr-core` (source-breaking, +73 net lines: +75 / -2):**
    - From `#1327` (additive): adds the `brokkr_core::work_order` module
      (`WorkOrder`, `WorkOrderId`, `WorkOrderState`, `Reference`,
      `Trackers`, `WorkOrderError`, `text_digest`).
    - From `#1410` (source-breaking): changes
      `realms::CapabilityGrant::dialect` from `String` to the closed
      enum `GrantDialect` (`Single(String)`,
      `PerProvider(BTreeMap<String, String>)`, implementing
      `From<&str>`), changes `realms::SCHEMAS` from `[&str; 8]` to
      `[&str; 9]` while adding `SCHEMA_V9`, and adds six variants to the
      closed enum `realms::GrantError` (`BothDialects`, `NoDialect`,
      `Dialects`, `DialectProvider`, `ProviderDialect`,
      `ProviderGrantKey`).
  - **`brokkr-store` (source-breaking, +17 lines):** adds
    `Damage::Orders` and `StoreError::Orders(OrderRefusal)` to closed
    enums (requiring new arms in downstream exhaustive matches, decision
    0071 ruling 2), plus `OrderRefusal` and `Store::{order, orders,
    order_add, order_edit, order_rule}`.
  - **`brokkr-runtime` (additive, +1 line):** adds
    `capabilities::Authority::provider_native_bindings` (`#1410`).
  - **`brokkr-protocol`, `brokkr-view`, `brokkr-bridge`,
    `brokkr-cli`:** unchanged.

## Supported platforms

Linux x86_64 and aarch64, and macOS x86_64 and arm64 (decision 0063).
WSL2 is Linux. Qoder's and agy's isolation, and `qwen4-max` on `dsh`,
are measured on Linux alone: on macOS nothing is measured for them, and
a boxed agy seat does not launch there.

## Install or upgrade

Download the `v0.16.1` archive and `SHA256SUMS` from the GitHub release
once published, and verify the digest before unpacking:

```console
curl -LO https://github.com/feedback-loop-ai/brokkr/releases/download/v0.16.1/brokkr-linux-x86_64.tar.gz
curl -LO https://github.com/feedback-loop-ai/brokkr/releases/download/v0.16.1/SHA256SUMS
grep ' brokkr-linux-x86_64.tar.gz$' SHA256SUMS | sha256sum -c - && tar xzf brokkr-linux-x86_64.tar.gz
```

Other channels — crates.io, apt, rpm, Homebrew and Nix (see
[README](../../README.md#install)) — update after the GitHub release as
each publishes or merges its channel pull request; `flake.nix` remains
at `0.16.0` until its update pull request merges. A running
`brokkr queue dispatch` exits cleanly on its next pass after binary
replacement, after which you can start `brokkr queue dispatch` on
`0.16.1`.
