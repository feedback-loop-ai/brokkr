Status: proposed. The law is decision 0094, proposed; only the operator accepts it.

## Goals

1. `brokkr run --recipe R --enter <gate> [--continues <run>]...` for any recipe, admitted or refused when the recipe and the entry are compiled, before a run id is minted or an event is written.
2. A run entered at `verify` over a finished branch reaches `SHIP-COMPLETE` with no intake, design or first-implement seat, proven on a synthetic recipe and repository.
3. The journal records, typed, the entry and the runs continued; the run view names them, feature first; the gate vouches the branch and names the chain.
4. Nothing skips verification or review that today's tables do not already skip: review stays unavoidable from wherever a run begins, and a work phase is reached in an entered run only by a return.
5. No ordinary run's seat input, manifest, witness or admission moves.

## Non-goals

The proposal's "Left out, and why" stands whole. In addition: no edit to `assert_phase_unavoidable`'s refusal text, no `queued-launch/v2`, no entry on a Looper-bound run, no fetch of a continued run's evidence by the gate, no `default` case added to `recipes/triage`, no edit to any file under `agents/charters/` or `recipes/*/roles/` by this run (D16), no answer to decision 0060's two open items (DD10).

## Decisions

### DD1 — The flag, not the overlay

`brokkr run --enter <phase>`, with `--continues <run>` repeatable, declared on `brokkr run`'s own arguments (D18). The composed overlay was weighed and not chosen, and decision 0094 records why among what it set aside: an overlay's `initial` cannot be told from a recipe's own first phase, so the compiler could not refuse a work-phase entry without a second marker; a recipe is static data and cannot name the runs one re-drive continues; and an adopter would write one overlay per recipe and gate, each restating one word, the copy ruling 5 forbids. The overlay road stays what it is, a recipe's own `initial` (`landing`, `review-first`), and an entry composes over it.

### DD2 — The admission is one function in one new module, run at two moments, and it returns a receipt

`crates/brokkr-runtime/src/bundle/entry.rs`, a child of `bundle.rs` beside `phases.rs`: `bundle.rs` is over its ceiling, so it gains the one `mod` line and pays for it (DD13). The module holds:

- `pub fn admit(bundle: &Bundle, phase: &str) -> Result<AdmittedEntry, EntryError>`: the six facts of the `gate-entry` delta, judged in order, each one private function within ruling 4's ceilings. It runs after the ordinary compile, over the compiled seat tree (robustness: fact 3 needs `SeatBody::is_gate` over every site, which only the compiled tree answers), and the bundle's own audit from `initial` is untouched: the entry is a second question put to a bundle already admitted, never a rewrite of `initial` before the audit.
- `pub struct AdmittedEntry` holding the phase, constructed only by `admit` (a private field, a `phase()` reader). `Engine::start_in_world` takes `Option<&AdmittedEntry>`, so the engine's start cannot be handed a phase no admission judged (ruling 3: the type carries the invariant a comment would ask for).
- `pub fn admitted(bundle: &Bundle) -> Vec<String>`: the phases `admit` accepts, in `phases` order, the one derivation of the refusal's "the table admits" list and of the table-lint pins (D8; ruling 5).
- `pub enum EntryError` (`thiserror`, ruling 8), one variant per refusal the delta names, each carrying the phase, its witness and the admitted list, its `Display` the operator's text: `Absent`, `Terminal` (fact 1); `Unprintable` (fact 2); `Work { site }` (fact 3, the first driver-bearing site that is work, named as `bounded_site` names a site); `AvoidsProtected { protected, terminal }` (fact 4); `ForwardWork { work, rule }` (fact 5); `NeedsStrategy { seat, reached_by }`, `NeedsStrategyRuling { group, reached_by }`, `NeedsChange { step, sources, reached_by }` (fact 6, in that rank). `LaunchError` gains `Entry(#[from] EntryError)` and `EngineError` the same, so the launch and the resume refuse with one text.

The two moments: `launch::start` calls `admit` right after `admit_new` compiles the bundle and before the store is opened, so an operator's typo costs no journal; `Cursor::Start` calls it again on the journaled entry (DD4). One function, two callers, no second rule (ruling 5). An `EntryRequest` is the untrusted input (`NewRun.entry: Option<EntryRequest { phase: String, continues: Vec<String> }>`, the ids already canonical, DD7); it never reaches the engine.

Alternatives: a `CompileError` variant (the framing's wording) was not taken because the compile is unchanged and succeeds; the entry is refused after it, by its own enum, and `CompileError`'s text pins do not move. A receipt carrying the manifest digest and checked by `start_in_world` was not taken: the launch compiles once and hands the same bundle, so the check is unreachable in production, and ruling 9 would then ask for a removal-control test of a guard no path takes; the journaled re-admission at `Cursor::Start` is the cross-process check that is reachable.

### DD3 — The six facts are read off three existing primitives, one roster and one predicate

Nothing in `entry.rs` walks the raw table. Every fact reads `bundle.machine` (typed `Rule`s) and `bundle.seats`:

- **Facts 1 and 2** read `machine.phases`, `machine.terminal`, `is_identifier` and the 64-byte bound. The bound and the grammar are one constant pair in `brokkr_core::policy` beside `is_identifier` (`ENTRY_NAME_MAX`), so the gate test holds one value (D6).
- **Fact 3** is `seats[phase].body.is_gate()`, with the first work site named by walking the same cases `is_gate` walks (one private `first_work_site` beside it, so the predicate and its witness cannot disagree).
- **Fact 4** calls one core walk made public: `Machine::reach_avoiding(&self, start, avoid: &[&str]) -> BTreeSet<&str>`, the private `reach` generalised to an avoid set (its one caller `advances` becomes a line over it). The fact holds when `start == protected` or when the set from the entry avoiding the protected phase holds no non-stop terminal. `assert_phase_unavoidable` is rewritten to the same call over `machine.initial`, its refusal text byte for byte as today, so the law has one home (ruling 5) and `bundle.rs` shrinks by the walk it no longer carries (DD13). Decision 0051's constitutional lint is then one function with two seeds.
- **Fact 5** is a breadth-first walk from the entry over the rulings `Direction::of(&machine.phases, &rule.from, next) == Some(Direction::Forward)`, a park (`next: None`) drawing no edge, each phase visited once, rules in table order; the first phase met whose seat fails fact 3 is the witness with the ruling that reached it.
- **Facts 6a and 6b** share one breadth-first walk over every ruling that never enters the strategy phase (`brokkr_core::policy::STRATEGY_PHASE`, made `pub` for this one consumer): at each phase met, first the seat's selector (`SeatBody::Select` with `default: None`), then each `(phase, result)` group of that phase that `Machine::unruled_without(&self, "strategy_in")` reports unruled. That core function is one function beside `sweep`: the sweep of every group over its rules that carry no condition of the named kind, returning `Finding::Unruled` as the sweep does today; the admission keeps the findings whose phase the walk met. `Condition` and `Rule::when` stay private; the core answers the question, the runtime does not read the guard.
- **Fact 6c** is, for each dialect step that `needs_change` (the predicate `engine/sequence.rs` already holds, made `pub(crate)`), in `phases` order and step order: covered by an earlier step of its own sequence when the seat declares `change` (`carry_change`'s rule); else refused when `machine.reach_avoiding(entry, &sources)` contains the step's phase, `sources` being the phases of `CHANGE_SOURCES` listed before the step's phase whose seat declares `change`. `CHANGE_SOURCES` is the roster in `phase_name.rs` that `nearest_change` reads too (D11, ruling 5). The "walk per step" of D17 is this reach with the step's sources removed; no third traversal is written.
- **The rank** (D17): the first failure of the selector fact, else of the group fact, else of the step fact, each with its own walk's first witness; `admit` returns the first `Err` in fact order, so a table that fails two facts names the one listed first.

`brokkr_core::policy::Direction { Forward, Return, Loop }` with `pub fn of(order: &[String], from: &str, next: &str) -> Option<Direction>`, `None` when either phase is not in `order`: the one predicate fact 5, DD6's return rule and DD8's roads back call (D5, D19; rulings 5 and 7). `Loop` is a phase ruled onto itself; a caller matches all three exhaustively (ruling 2).

Alternatives: a `SeatClass` read off `seat.class` or a selected happy-path body (refused: an empty or selected body does not prove every executing site is a gate, robustness); a name list of enterable phases (refused: the engine holds no roster, decision 0021 ruling 1's reasoning); the raw-table walk copied into `entry.rs` (refused: a third copy of the reach).

### DD4 — The engine reads the entry from the journal at `Cursor::Start`, typed once, and refuses a bad one

`Engine` gains a field `entry: Option<RunEntry>` (the core type, DD5), set at `start_in_world` from the admitted entry and the resolved chain, and at `resume` from the first event's payload, where `charters` is already read. `advance_running`'s `Cursor::Start` arm becomes one call, `engine::entry::first_phase(&self.bundle, self.entry.as_ref())`, in a new module `crates/brokkr-runtime/src/engine/entry.rs`: no entry is `machine.initial`; an entry is `admit(bundle, phase)?.phase()`. A `run/started.entry` that does not parse is refused where it is read (`resume`), and one that no longer admits is refused at `Cursor::Start`, each by `EngineError::Entry`; nothing falls back to `initial`. The resume window the delta names (a journal ending at `run/started`) is this arm, and the manifest gate before it proves the bundle is the one that admitted the entry.

`nearest_change` moves into the same module, over `CHANGE_SOURCES`, so `engine.rs` loses more lines than the call it gains (DD13). `is_native_run_id` lives there too, beside the mint's shape, with a test holding a freshly minted id to it.

### DD5 — The journal: two additive fields, typed at the edge, read by the fold never

`Bundle::run_started` gains two members (the one home, `bundle/origins.rs`): `phases`, the compiled table's `phases` list verbatim, on every start; and `entry`, `RunEntry` serialised, only when the start carries one. `brokkr_core::entry::RunEntry { phase: String, continues: Vec<ContinuedRun> }` and `ContinuedRun { run_id: String, feature: String }`, `serde` with `deny_unknown_fields` on both (ruling 3), in a new core module beside `envelope.rs`. One reader, `RunEntry::of_started(payload: &Value) -> Result<Option<RunEntry>, EntryRead>`: the key absent is `Ok(None)`; the key present with any value, `null` included, parses whole or is `Err` naming what did not read. The engine, the seat input and the view read through it and nothing reads `entry` by string key past that edge.

The fold reads neither field; `RunState` gains nothing; `verify-run` checks envelopes whose payload the v1 schema types as an object. Under the amended rule (`contracts/README.md`, decision 0016) each is an additive, optional, absent-by-default field; `phases` follows `charters`, which every start already writes; `entry` follows `layers`. Their numbered extension schema is minted when the operator accepts decision 0094 (decision 0082 ruling 1); until then the decision and the Rust types are their shape, and `contracts/README.md`'s extension paragraph names both fields under proposed 0094 so the vocabulary is published where the house publishes it. Every journal written before this change folds, verifies and views as it did (DD8 for the rail).

Alternatives: a typed `run/entered` event (refused: the event-type enum is closed under `additionalProperties: false`); the entry inside the manifest (refused: a manifest version under a proposed decision, and a second home); `phases` on entered runs only (refused, DD8).

### DD6 — What a seat is told, and the return rule

`seat_context` (`engine/input.rs`, 224 lines, room to grow) inserts `context.entry` from `self.entry`, serialised as `RunEntry` is, under the guard it already holds for `last_decision` (`phase != TRIAGE`), so triage reads nothing of it (D14) and an ordinary run's context is byte for byte what it was. `returned_from` is handed when `visits > 1`, as today, or when the run has an entry and `Direction::of(&machine.phases, &last_decision.from, phase)` is `Some(Return)`, `phase` being the one `seat_context` is building the input for, which is the ruling's `next` (D5, D19): the ruling's direction, never the entry's position. A run without an entry keeps the first clause alone, so no input digest of a mid-flight run moves (the delta's "A run without an entry builds the inputs it always built"). The continued runs' results are not handed: `context.results` is built from `state.phase_results` as today.

Alternative: extending the return rule to every run (refused for now, the proposal's "Left out": it rebuilds every mid-flight landing's input digest; a later story).

### DD7 — The chain is resolved once, held canonical, and refused before any event

In `verbs/delivery.rs`, `brokkr run` resolves each `--continues` selector through `selector::resolve_run` against the journal `Invocation::resolve` named, as every `--run` is resolved, and builds `NewRun.entry = Some(EntryRequest { phase, continues })` with canonical ids; `new_run` itself, which `queue add` shares, sets `entry: None`. `launch::start` then, after the bundle is compiled and the entry admitted and before `Engine::start_in_world`: refuses an entry beside a dispatch (`LaunchError::EntryWithDispatch`, in the same breath as `RealmsWithDispatch`); opens the store; and for each id in order refuses one named twice (`ContinuedTwice`), one the store does not hold (`ContinuedMissing`), one outside `is_native_run_id` (`ContinuedOutsideGrammar`, D13), and one whose folded status is not `completed` or `stopped` (`ContinuedNotConcluded { status }`, decision 0092 ruling 4), reading each feature through `source_feature`. The result is `Vec<ContinuedRun>`, handed to `start_in_world` beside the `AdmittedEntry`, and written into `run/started.entry.continues` in the order named. Nothing re-resolves `latest`: resume and every view read the ids the start recorded (robustness).

`--continues` without `--enter` is refused by `clap` (`requires = "enter"`), and the runtime cannot express it: the continues live inside `EntryRequest`.

### DD8 — The view derives the entry once and orders the rail by the recorded order

`brokkr-view` gains two child modules of `lib.rs`, which is over its ceiling: `entry.rs`, deriving `RunView.entry: Option<EntryView { phase, continues: Vec<ContinuedView { feature, run_id }>, text }>` from `RunEntry::of_started` on the first event, and the pure `pub fn entry_sentence(entry: &RunEntry) -> String` that writes `entered at <phase>, continuing <feature> (<id>)` per run in order, or `entered at <phase>, continuing no earlier run` (D21); `rail.rs`, into which `phase_rail` moves whole from `lib.rs` and where it changes.

The rail (D19): the order is `run/started.phases` when present and a list of strings, else first entry. Each phase the journal entered stands once in that order with its visits; a phase the order does not name stands after them by first entry. A road back is a `transition/decided` whose `Direction::of(&order, from, next)` is `Some(Return)`; `Forward`, `Loop` and `None` draw none. Because the same predicate runs over the first-entry order when no order was recorded, a journal from before this change reads exactly as #813 drew it (its "strictly before on the rail" is `Return` over that rail), so the fallback is the same code and not a second rule. A `phases` present but unreadable is treated as absent by the view, which cannot refuse a journal the fold accepts and never repairs what it cannot read (law 2); the engine reads `phases` from no journal, so no control decision rests on it.

`VIEW_VERSION` moves to 25 (`origin/main` is at 24 after #813, Migration) and `extensions/dsh/brokkr-console/lib/host/readouts.js` pins 25. The painters only paint: the console's run header (`client.js`, beside the worktree line, as text nodes), `ui.html`'s header beside the boundary badge, the TUI's header line in `tui/panes.rs` (`graph_rows` counts it as it counts the boundary line). The console's `roadsOf`, the TUI's `returns_of` and `ui.html`'s `returnPairs` are unchanged: every road the rail now names lands left of its departure, the one geometry they draw.

### DD9 — The gate reads the chain, prints ids, and its claim is narrowed in writing

`scripts/delivered-by-brokkr.sh` gains one jq read over the verified journal's `run/started.payload.entry`: absent, the check line is today's; present, it must be an object whose `phase` matches `^[a-z0-9][a-z0-9._-]{0,63}$` and whose `continues` is an array of objects each with a `run_id` matching `^[a-z0-9-]{0,32}-[0-9a-f]{8}$`, else `fail` names the run and the unreadable entry (a refusal the by-hand label may override, logged as every skip is). The `vouched` line becomes `run <id> vouches for <head> · entered at <phase>, continuing <id>, <id>`, ids only, never a feature. Nothing else in the script moves: the tier is still cut by the anchor's patch map from the merge-base, which spans every commit on the branch whichever run or hand made it (decision 0038 ruling 1), and `fetch_evidence` is called for no continued run.

The claim, written into decision 0094: the gate vouches the shipping run's whole-branch patch map and reports the runs the operator named; it imports no result, verify, review, counter or security clearance from them, and a missing or unpublished predecessor supplies no authority and skips no gate. The framing's "fetched and verified like `Brokkr-Preflight`" is refused with its reasons: a continued run stopped before any anchor existed and `verify_evidence` requires a completed anchored run; a check that holds only sometimes reads as a verification it is not (D7); and the patch map already spans the commits a predecessor's journal could only vouch a subset of.

One test in `tests/delivered_by_brokkr.rs` reads the script's text and holds its two patterns equal to `ENTRY_NAME_MAX` with `is_identifier` and to `is_native_run_id`, over a corpus of boundary cases, so neither grammar can drift from the compiler's or the launch's. `.github/workflows/ci.yml` is unchanged; the base branch's copy of the script judges this pull request and ignores `entry` (Migration).

### DD10 — `landing` and `review-first` stay recipes; the law they share is the compiler's
