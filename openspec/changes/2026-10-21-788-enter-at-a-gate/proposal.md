# Change: a run of any recipe enters at a gate over work already on the branch, continuing the runs it names (#788)

Status: proposed. The law is decision 0094, proposed; only the operator accepts it.
Change: `2026-10-21-788-enter-at-a-gate`.
Parent story: [#788](https://github.com/feedback-loop-ai/brokkr/issues/788), part of epic [#790](https://github.com/feedback-loop-ai/brokkr/issues/790) (cheaper recovery). Beside it: decision 0092 (#789, on `main`) parks an environment block inside the run so one seat is retried; #787 (decision 0093, in the merge path) retries one panel member. This change recovers the run that has already ended, and keeps clear of both.

## Why

`stopped` is terminal. A run whose work is finished and committed, and which then stopped at a hard rule or exhausted a gate's attempts, has one road back: a fresh run of the same recipe, which begins at the table's `initial` phase, repeats intake and design, and lets the design seat commit again over a branch that already holds the design. The shipped `landing` recipe is `fast` entered at a classify gate, but it is Brokkr-only (`extends brokkr-fast`), it begins where a branch written by hand begins, and it says nothing about the runs whose work it finishes. Every other recipe (an adopter's own frontier recipe, say) has no later entry. Over 2026-10-18 and 19 one adopter's epic re-drove six runs, each spending 15–25 minutes and a design commit on intake and design before it reached verify.

A recipe already knows which of its phases judge and which write: every driver-bearing site carries a class, `gate` or `work` (decision 0021 ruling 1), and the compiler already walks the table from `initial` to refuse a path to a terminal that avoids the protected phase. What is missing is one word the operator can say at start, `enter`, and the record of what the entered run continues.

## What Changes

- **The entry.** `brokkr run --enter <phase>` starts the run at the named phase of the table it runs under, instead of the table's `initial`. The table, the compiled bundle, its digest, the run manifest and the witnesses do not move: an entry is a fact of the run, journaled, not of the recipe. A recipe whose own `initial` is a gate (`landing`, `preflight`, `review-first`, `verify`) starts as it always did when no entry is named, and its `initial` is itself an entry when it passes admission: `--enter classify` on `landing` is a landing that names the runs it continues.
- **Admission, at compile.** Six facts of the table and its seats, judged in this order, the first that fails named in a typed error with the phase, the fact, its witness and the entries the table admits, in the order of the table's `phases` list, before a run id is minted or an event is written:
  1. the phase is one of the table's and is not a terminal, so it is seated;
  2. its name is one the contribution gate prints without a forgery: `^[a-z0-9][a-z0-9._-]{0,63}$`, the dialect's identifier grammar bounded to 64 bytes. The table loader bounds no phase name, so this is the compiler's own check, and it never admits an entry the gate refuses;
  3. every driver-bearing site of its seat is a gate (decision 0021 ruling 1: a single by its class; a sequence by its steps, each written `gate`, a dialect step included, since an undeclared site is work; a panel by its members; a selector by every case and its default). That is the seat's compiled whole-gate fact, `has_gate`, the one the dispatch door journals as the effect's `gate` (D24), and the witness is the first site whose class is work in the seat's written order, a dialect step by the class it wrote, and one the realm's dialect does not supply, which compiles no site, named by its step name and written class as uncompiled (D29);
  4. the protected phase (`protected_phase`, `review` unless the bundle names another) is the entry itself or is unavoidable from it: the walk the compiler already makes from `initial` (`assert_phase_unavoidable`, decision 0051's constitutional lint), started at the entry;
  5. no work phase is met by the forward walk from the entry, a forward ruling being one whose `next` stands after its `from` in the `phases` list, a park drawing no edge and a self-loop reaching nothing new: so a work phase is reached in an entered run only after a return, which is the commission's "implement is entered only on a return" made mechanical for every work phase;
  6. no seat, step or ruling group the walk meets needs a journal fact that only a phase the walk does not enter can set. Three such facts exist, and the table holds no others. `strategy`, which only the strategy phase's ruling sets (`triage`, decision 0041 ruling 6), is needed by a seat that selects on it with no `default`, since that seat has no body otherwise, and by a `(phase, result)` group that holds any ruling conditioned on `strategy_in`, whatever its other rulings rule, since an absent `strategy` satisfies no `strategy_in`, so such a ruling never matches in the entered run where a run started at `initial` may match it, and a hard denial a strategy decides would fall through to an unconditioned allow below it (amended by D36, which records the totality reading this replaces). The dialect's `{change}` is needed by a dialect step that expands it, and its source is an earlier step of the step's own sequence when the seat declares `change`, else a result of one of the five phases `nearest_change` reads (`tasks`, `design`, `specify`, `triage`, `intake`), listed before the step's phase, whose seat declares `change`, and only when every road from the entry to the step enters such a phase. A seat, step or group that needs a fact the walk cannot supply is a refusal naming it and the fact.

  The walk is breadth-first from the entry, the entry's own seat first, then every ruling of each phase in the table's rule order, phase by phase in the order first reached, each phase visited once, a park drawing no edge. Fact 5 follows forward rulings alone. Fact 6 is three facts judged in their listed order, each over its own walk: the two `strategy` facts over one walk that follows every ruling but never enters the strategy phase, unless the entry is itself the strategy phase, which sets `strategy` by its own ruling before any other phase is met, so both hold and no walk is taken for them (D34); the `{change}` fact over one walk per dialect step whose sources do not include the entry (an entry that is one of them covers the step, D33), the steps taken in the order of the `phases` list and, within a seat, in step order, that follows every ruling but never enters a source phase of that step. The witness a refusal names is the first failing fact's first witness in its own walk's order, with the ruling that reached it, so a table that fails two facts of six names the one listed first, and the next refusal names the next (D17).

  The engine holds no roster of which phases may be entered: the facts are the table's and its seats', and the admitted set is derived by the same six facts. In every `fast`-shaped table that admits `verify` and `review` and refuses `implement` and `ship`. The commission listed `ship` among the gates; it is refused by fact 4 because `SHIP-COMPLETE` reaches `done` without review, so an entry at `ship` would let a run's own journal vouch for a head no seat of that journal judged, which is the one thing the contribution gate rests on. The recovery for a ship that failed is decision 0092's retry when it parked, or an entry at `review`, one judge's read, when it stopped. The `triage`-shaped tables (`triage`, `gpt-flash`, `night-shift`) admit no entry today, each refusal naming its own first fact (D22). In all three `triage` fails fact 5, since `TRIAGE-CHORE` reaches `implement` forward; `clarify` and `analyze` fail fact 3, since their dialect `check` steps declare no class and an undeclared site is work; `ship` fails fact 4. In `triage` and `night-shift`, `verify` and `review` fail fact 6: `review` selects on a strategy only `triage` rules and carries no default, so an entry there is refused on its own seat; from `verify`, `triage` names `implement`, reached by `VERIFY-FAIL`, which selects the same way, and `night-shift`, whose `implement` is a plain work seat, names `review`, reached by `VERIFY-PASS`. In `gpt-flash` no fact 6 is ever judged: its `review` cases are sequences whose `positions` panel is written `work` ahead of a `chief` written `gate`, so `review` is a work phase and fails fact 3 on that panel, and `verify` fails fact 5, `VERIFY-PASS` reaching `review` forward. The road to an entry is the recipe author's and is named here, not ruled: a `default` case on a selecting seat, and gate-classed judges where a work site stands in a judging phase. Brokkr's own re-drive road stays `landing` (decision 0051 ruling 4), which now names the run it continues.
- **An entry at review.** The protected phase is an entry wherever the six facts admit it, `landing` included, and a run entered there holds no verify in its own journal: it vouches a head no seat of that journal tested. That is the operator's word, as the chain is, and the record says so on every surface: `run/started.entry.phase`, `context.entry`, the run view and the gate's check line all name the gate entered. The by-hand road is untouched: a landing started without an entry classifies the branch, and one code path still routes to verify (decision 0051 ruling 3). Decision 0094 records the departure and why (D10).
- **The return.** In an entered run a seat receives `returned_from`, the ruling's phase and the result that sent the run there, on its first visit when the ruling that sent it is a return, a ruling whose `next` stands before its `from` in the `phases` list, the order `seat_context` already reads `context.results` in. A forward ruling into a phase this run has not visited hands nothing new, exactly as a first visit does today; a revisit hands what it always did; triage receives nothing on any visit (decision 0041 ruling 6). The rule reads the ruling's direction, never the entry's position, so no table order can send a smith back without the finding. One predicate of `brokkr-core`, `policy::Direction::of(order, from, next)`, a closed enum `Forward`, `Return` or `Loop` and `None` for a phase the order does not name, says it; the admission's fact 5, this rule and the run view's roads back read it and nothing else decides a direction (D19). No seat input of a run without an entry moves.
- **The chain.** `--continues <run>`, repeatable and only with `--enter`, names the earlier runs the entered run continues, each a full id, a unique prefix or `latest` in the journal the run is written to. A named run must exist there and be concluded, `completed` or `stopped`: a running one is still at work, and a parked one is resumed or concluded first (decision 0092 ruling 4). A run named twice is refused. Each named id must match the native run-id grammar the contribution gate reads, `^[a-z0-9-]{0,32}-[0-9a-f]{8}$`, the shape the engine mints, so a start admits no chain the gate refuses. Every Looper-bound run is refused as a run to continue, told apart by what its start pinned, the Looper-bound run-manifest/v2 lineage (`forge-run-manifest/v2`), never by its id, whose shape may be native (D28). Every refusal comes before an event is written. The chain is the operator's word: the engine verifies existence, conclusion, the grammar of the id and the lineage its start pinned, and nothing else, and every surface says the chain as named at start. An entry that names no run is admitted: a branch with no run to continue, entered at a gate, is what a landing is.
- **The journal.** `run/started` gains two optional fields. `entry`: the phase entered, and the continued runs in the order named, each by its id and the feature its own start recorded, so every reader leads with the words; `continues` is always present, an empty array when no run was named, so no reader tells an empty chain from an absent one by a missing key; it is absent on every run without an entry. `phases`: the compiled table's `phases` list, verbatim and in its order, written on every start, the Looper-bound one included, so a reader that holds no bundle, the run view above all, reads the order the engine rules by (D19). A run without an entry then carries `feature`, `manifest`, `charters`, `layers` where composed, and `phases`, and no `entry` key. Every journal written before folds, verifies and views as it did. The engine change moves no manifest, table or charter witness; the charter edit below moves, as any charter edit does, the witnesses of the charters edited and of the bundles that bind them, `landing`'s marker moves its own table and bundle rows (D37), and nothing else moves (D9). The fold reads nothing of either; the engine reads `entry` at start and at resume to enter the entry instead of `initial`, and reads `phases` from no journal, since it holds the table. Each is an additive, optional, absent-by-default field under the vocabulary's amended rule (decision 0016's amendment in `contracts/README.md`), as `charters` and `layers` are; their numbered extension schema is minted when the operator accepts decision 0094 (decision 0082 ruling 1), and until then the decision and the Rust types are their shape.
- **What the seats are told.** Every seat of an entered run except triage receives `context.entry`, derived from `run/started.entry`: the phase entered and the continued runs, each by `run_id` and `feature`. Triage reads no journal, no fleet and no history (decision 0041 ruling 6), and the chain is history: its input carries none, as it carries no `last_decision` and no `returned_from`. `context.entry` is absent from every seat input of a run without an entry, so those inputs and their digests do not move. The continued runs' results are not handed: the branch, the feature text and the chain are what the seat knows.
- **What the review judges.** The contribution gate vouches the whole branch from its merge-base with the default branch, whichever run or hand wrote it, so that is what a review seat judges. The five charters whose scope reads "everything since the run began" (`agents/charters/reviewer.md`, `review-correctness.md`, `review-security.md`, `review-adversarial.md`, `node-reviewer.md`) and the two copies pinned byte for byte to the first (`recipes/review-first/roles/reviewer.md`, `recipes/standby/roles/reviewer.md`) now scope the delivery as everything on the branch since its merge-base with the default branch, the cut the anchor makes (decision 0038 ruling 1), which on a fresh branch is everything since the run began, and say that `context.entry` means the branch holds the work of the runs it names and all of it is the seat's to judge. A library test, `crates/brokkr-runtime/tests/review_scope.rs` (D36), holds those seven to the clause by path, and every charter under `agents/charters/` and every `roles/*.md` under `recipes/` to one textual rule: none scopes its read to the run's beginning or the pre-run commit; the starter reviewer charter `brokkr init` writes for an adopter takes the same clause, held by its init test (D36's F2, D37). `verify-reviewer.md` reads the range the feature text names, `review-spec-compliance.md` judges the change's whole diff, and `recipes/preflight/roles/reviewer.md` already reads `main...HEAD`, the merge-base cut; the three are unchanged and held by the rule alone (D15). Three of the seven, `review-adversarial.md`, `review-correctness.md` and `review-security.md`, are the charters the first implementation's review panel was pinned to, and the dispatch door refuses a charter whose bytes moved since the compile (decision 0066 ruling 5), so that run wrote none of the seven (D16); the clause, its test and the pins that follow the bytes landed by hand on this branch after that run stopped and before the run that implements D36's settlement started, so the settlement's panel compiles over the clause and judges the whole branch from its merge-base, the first implementation included (D36's F2), and the landing that vouches the final head follows as D20 says.
- **The view.** `RunView` derives `entry` once: the gate entered and the continued runs, each led by its title, `brokkr_view::title` of its feature, with its id after and the whole feature kept in its parts, as named at start, and the one sentence that says it, one line however many lines a feature holds (D26); a present `entry` it cannot read it states as unreadable with the reader's error, never painting the run as an ordinary one (D27). The console's run header, `brokkr ui` and the TUI paint it and derive nothing of their own; `brokkr run` keeps `run started: <id>` exactly as it is, the id alone on its line, and prints that sentence on a line of its own after it (D21); nothing is painted for a run without one. The rail stands in the order the start recorded, `run/started.phases`, each entered phase once with its visits, and a road back is a ruling `Direction::of` calls a return over that order, so an entered run's return into a phase listed ahead of its entry, and a landing's, is drawn once by the ruling that took it, and the forward step after it is not; a journal whose start recorded no order keeps first entry, as #813 drew it (D19). The wire moves to one past `main`'s at the merge, 27 expected behind #787's 26 since #808 took 25, and the console host's pin with it (D25, amended by D36).
- **The gate.** `scripts/delivered-by-brokkr.sh` vouches an entered run as it vouches any run: the ship anchor's per-file patch map is cut from the merge-base of the default branch and the vouched head, so it spans every commit on the branch, whichever run or hand made it, and the tier is cut by the delta since that judgment (decision 0038). The gate reads `entry` from the vouching run's verified journal and names the gate entered and each continued run's id on its check line, never a feature text; an `entry` it cannot read, a phase outside the grammar admission applied, or a continued run outside the native run-id grammar, is a refusal, never a vouch; an absent one reads as today. One test holds the script's two patterns to the compiler's and the launch's. It fetches no continued run's evidence: a continued run stopped before any anchor existed, and its journal is not required to be published.
- **`landing`.** It stays a recipe, and the design says precisely why: it adds a seat, `classify`, and two rules, which an entry cannot express; it is the by-hand road, where the gate is chosen from the branch's class rather than from the operator's word (decision 0051 rulings 1 and 3); and its `initial` is a recipe's own first phase, which this change leaves untouched. Its bundle marks `phases` in `override.table`, beside `initial`, as `triage` and `panel-review` mark theirs, so the compiled table lists `classify` first as its own table writes it, where the union composition listed it after the phases it inherits (D36's F3, D37). It shares the law: the protected phase is unavoidable from where the run begins, which the compiler held for every `initial` and now holds for every entry. An entry composes over it as over any recipe, admitting `classify`, `verify` and `review`. Decision 0051 ruling 4's road, relighting a judgment that could not land as a landing, keeps its text and gains the chain: the landing names the run it continues, and a stopped run of a recipe that admits its gate is re-driven there instead.
- **Not chosen: the composed landing overlay.** A derived recipe can set `initial` to a gate today; `landing` and `review-first` prove it, and that road stays for by-hand work. It was not chosen as the general mechanism, and decision 0094 records why: an overlay's `initial` cannot be told from a recipe's own first phase, so the compiler cannot refuse an entry at a work phase without a second marker; a recipe is static data and cannot name the runs one re-drive continues; and every adopter would write one overlay per recipe and gate, each restating one word (decision 0071 ruling 5).

### First visit

- **D1 (Q1, blocking). A skipped phase's fact is an admission fact, never a carried one.** The facts a seat may need from an earlier phase are closed: `strategy`, folded only from the strategy phase's ruling (`fold.rs`, `STRATEGY_PHASE`) and read by `SeatBody::selected`, `computed_inputs` and the `strategy_in` condition; and `{change}`, carried only by a step result of a seat declaring the `change` input (`engine/sequence.rs`) or a result in `context.results` (`engine.rs`, `nearest_change`). Counters are absent as zero, `reviewed_heads` is set by the protected phase this run visits before ship, and the rest are seat-owned. Option (a), the sixth admission fact, is taken; D11 states it by the engine's exact rules. Option (b), the entry carrying a typed strategy and change, was refused because selection and the `strategy_in` inputs read `RunState`, which is folded from this run's journal alone: the fold would have to read `entry`, and under the amended rule a field a consumer must read to fold correct state is a v2 event, which the frozen `{"const": 1}` of every manifest schema and the closed event-type enum rule out; a synthetic `transition/decided` from triage is refused by the fold's relation, which accepts a decision only at `Decide` after an effect succeeded, and would be a ruling no seat made. Option (c), reading a continued run's fold, fails the same way and would make an unverified chain (D7) a source of selection. Under (a) the triage-shaped tables admit no entry today, said in the refusal; the acceptance case, an adopter recipe that runs intake and design ahead of implement with no selector and no dialect, admits `verify` and `review`, and the acceptance fixture has that shape (D4).
- **D2 (Q2, high). The review judges the branch from its merge-base, and the charter says so.** The gate vouches the anchor's patch map, cut from the merge-base with the default branch (decision 0038 ruling 1), so a review scoped to "since the run began" would rule clean over commits no seat of the vouching run read, and the vouch would stand on nothing. The scope clause of every review charter that reads so moves to the branch since its merge-base with the default branch, the same cut, which costs a fresh-branch delivery nothing because the two cuts are the same commits, and closes the same latent gap in `landing`, whose README already claims the branch is judged against the base. The seats learn the chain from a typed fact present only in an entered run, `context.entry`, which keeps every other run's input byte-identical, and the clause names it. A charter clause is the mechanism because a seat is a model reading its charter: a typed fact alone would not move what it diffs. The refutation offered, that the review already reads the base under decision 0051, does not hold: decision 0051 ruling 1 changed one word of the table and no charter, and the charter text is what the seat reads.
- **D3 (Q3). "Implement is entered only on a return" is fact 5, for every work phase.** Not a recorded departure: an entry from which a work phase is reached forward re-runs design and tasks, the cost the epic exists to remove, and the earlier draft gave no reason. The forward road is defined by the `phases` list, the order the house already reads for `context.results`; a return is a ruling against it. A dialect gate whose steps are written `gate` is refused by it in every table shaped like the dialect's, since its road leads forward to design or implement (the shipped `clarify` and `analyze` fail fact 3 before that, their check steps declaring no class), and a dialect gate placed after implement in an adopter's table is admitted when its road holds.
- **D4 (Q4). Shapes are their phase lists, and the acceptance fixture holds intake and design.** `fast`-shaped: `implement, verify, review, ship, done, stop` (`fast`, `brokkr-fast`, `node`, `release`, `standby`, `review-first`, the three wager harnesses). `panel-review`-shaped: `intake` ahead of the same (`panel-review`, `self`). `landing`: `classify` ahead. `preflight` and `verify`: `verify, review, done, stop`. `research`: `research, verify, done, stop` with `verify` protected. `triage`-shaped: `triage, specify, clarify, design, tasks, analyze, implement, verify, review, ship, done, stop` (`triage`, `gpt-flash`, `night-shift`). The acceptance fixture's table lists `intake, design, implement, verify, review, ship, done, stop`, intake and design being work phases the stopped, continued run entered, and it binds no library charter; so a mutation that starts the entered run at `initial` enters intake and fails the proof, and a mutation that drops `entry` from the journal fails the view and the gate.
- **D5 (Q5). "Before" is the position in the `phases` list, and the return rule reads the ruling, not the entry.** A seat receives `returned_from` on a first visit when the ruling that sent it is a return (`next` before `from` in the list); the entry's own position decides nothing, so a table whose list puts a returned-to work phase after the entry needs no refusal: its smith is still handed the finding. The walk from `initial` was not used to define "before" because every phase of a delivery table is reachable from every other over its returns. The predicate is one function of `brokkr-core`, shared with the admission's fact 5 and the run view (D19).
- **D6 (Q6). One grammar for an entry's name, applied at compile and at the gate.** `^[a-z0-9][a-z0-9._-]{0,63}$`: `brokkr_core::policy::is_identifier`, the dialect's change grammar, bounded to 64 bytes as `bounded_site` bounds a label. The table loader checks phase names for nothing but being strings, so the compiler refuses a phase outside the grammar as fact 2, never admits an entry the gate refuses, and no phase name can forge a check line; a test holds the script's pattern to the predicate. The grammar is one function, `brokkr_core::entry::is_entry_name`, beside the record's reader, called by the compiler's fact 2, the record's check and that test, so the rule is written once (amended in place after analyze's fourth return, F2; the design's DD5). D13 applies the same rule to a continued run's id.
- **D7 (Q7). The chain is the operator's word.** `--continues` checks that each run exists in the journal the new run is written to, is concluded, carries an id the gate can read (D13), and was not started Looper-bound (D28, amending this in place), nothing more. A realm or repository check was refused because it would hold only sometimes: the store records no repository, a run started unmapped pins no realm, and decision 0051 ruling 4's road continues a run of another recipe; a check that sometimes passes would be read as a verification it is not. Every surface says the chain as named at start, and the gate prints the ids without fetching them.
- **D8 (Q8). The refusal lists the admitted entries in the order of the table's `phases` list**, the same order facts 5 and D5 read, pinned once per module (decision 0071 ruling 8). The witness it names is picked by the walk D12 defines.

### Second visit

- **D9 (Q1). A run without an entry carries no `entry` key, and the engine change moves no manifest, table or charter witness.** The earlier scenario promised that an ordinary run's `run/started` and every witness stand byte for byte while the same change edits five review charters; a charter edit moves the `charters` bindings `refuse_moved_charter` records in `run/started` and the manifest digest of every bundle that binds the charter, so the scenario could not pass. The invariant restated: a run started without `--enter` carries no `entry` key, and its `run/started` is what `Bundle::run_started` wrote before this change, `feature`, `manifest`, `charters` and `layers` where composed, plus the `phases` list D19 writes on every start, proven on the acceptance fixture recipe, which binds no library charter, by starting the same bundle with and without the flag: the one without carries no `entry`, both carry the same `phases`, and both pin the same manifest digest. The invariant is the absent key, every manifest, table and charter witness and every seat input, not the byte-identity of `run/started`, which D19 amends; the journal's payload-key witness, `crates/brokkr-cli/tests/witness_journal.rs`'s golden over a real run, moves by the one key `phases` on `run/started`, re-pinned with its comment citing decision 0094 ruling 6 (the design's DD13). The witnesses say the rest: the re-bless moves the `charters` rows of the five edited files and the `bundles` rows of every bundle whose composed seats bind one of them or pin one of the two copies, which on today's tree is every bundle but `preflight`, `research`, `research-dsh` and `verify` (`verify-reviewer` extends `reviewer` but names its own charter, which replaces the base's); every `tables` row but `landing`'s, which moves with its composed order (D37), every other `charters` row and those four `bundles` rows stand. That nothing else moved is the proof that the engine change moved no manifest.
- **D10 (Q2). An entry at the protected phase vouches a head no verify of the vouching run tested, and the record says so.** Option (a). The commission lists `review` among the gates an entry may name, and decision 0051 ruling 3 already lets a run ship prose that no verify of its own journal tested, on the ground that the platform suite on the pull request is the backstop; an entry at `review` extends that from "the class says prose" to "the operator says verified", and unlike the class it is written down. The gate never claimed a verify: it checks that the run ruled `shipped` and that the patch map matches, and its check line names the gate entered, so a reader of the pull request sees that this run's own journal holds no verify. How it squares with decision 0051 ruling 3: that ruling governs the landing's by-hand road from its `initial`, where the operator has said nothing and `classify` reads the class in that silence; `CLASSIFY-CODE` to verify is untouched. An entry is the operator's word, as the chain is (D7), and it is journaled where a classify ruling is not. So `--recipe landing --enter review` over a code branch is admitted, enters review first, and forges no classify ruling: the journal holds no `phase/entered` for `classify` and `entry.phase` reads `review`. Option (b), promoting verify to a compiled role and refusing an entry from which verify is avoidable, was refused: it refuses `review` in every shipped table and `classify` in `landing`, against the commission's own list, and it would make a landing's `initial` not an entry. ## Left out, and why

- `brokkr rerun --enter`: a rerun is a past run's feature from the beginning. An entered run states its own commission, what the branch is and why, as a landing does (decision 0051), so `--feature` stays required.
- Queueing an entered run: `--enter` and `--continues` are `brokkr run`'s flags alone, declared apart from the launch arguments `brokkr queue add` shares, so `queue add` refuses them as arguments it does not know; and `QueuedLaunch::of` refuses a `NewRun` that carries an entry, by name, rather than widening `queued-launch/v1` in silence (D18). A `queued-launch/v2` waits on a queue that asks for it.
- An entry on a Looper-bound run (`--dispatch`) is refused by name, as a named map is: the v2 manifest lineage and the bridge's normalized `run/started` carry no entry, and a counterpart would be told nothing. Continuing a Looper-bound run is refused too, every one, by the run-manifest/v2 lineage its start pinned and not by its id's grammar, which a Looper id may satisfy (D13, D28).
- The continued runs' results are not handed to the entered run's seats (D1): the branch, the feature text and the chain are what a seat knows, as a landing knows them. Nor is a continued run's verify read or compared (D10): an entry at review is the operator's word, journaled.
- A `default` case for the `triage` recipe's selecting seats, which would let a triage-shaped table admit `verify` and `review`: a recipe change with its own identity move, the author's to propose.
- The fleet list, `brokkr runs` and the bridge's normalized `run/started` (manifest only) are unchanged.
- A journal written before this change carries no `phases`: its rail stays in first-entry order and its roads back read as #813 drew them, a `landing`'s or `review-first`'s first return included (D19). The view guesses no order it was not given.
- A landing's first return still receives no `returned_from`: a recipe's own `initial` is not an entry, and this change moves no seat input of a run without one. The return rule of D5 would close it if extended to every run, at the cost of every mid-flight landing's rebuilt input digest; a later story.
- The return bound counts implement visits (decision 0022), so an entered run, like a landing, allows one return more than a delivery. Named, not changed.
- Promoting `verify` to a compiled role of the bundle (`phase_name.rs` says it waits on a decision): D10 refused the only use this change had for it.
