# Change: a run of any recipe enters at a gate over work already on the branch, continuing the runs it names (#788)

Status: proposed. The law is decision 0094, proposed; only the operator accepts it.
Change: `2026-10-21-788-enter-at-a-gate`.
Parent story: [#788](https://github.com/feedback-loop-ai/brokkr/issues/788), part of epic [#790](https://github.com/feedback-loop-ai/brokkr/issues/790) (cheaper recovery). Beside it: decision 0092 (#789, on `main`) parks an environment block inside the run so one seat is retried; #787 (decision 0093, in the merge path) retries one panel member. This change recovers the run that has already ended, and keeps clear of both.

## Why

`stopped` is terminal. A run whose work is finished and committed, and which then stopped at a hard rule or exhausted a gate's attempts, has one road back: a fresh run of the same recipe, which begins at the table's `initial` phase, repeats intake and design, and lets the design seat commit again over a branch that already holds the design. The shipped `landing` recipe is `fast` entered at a classify gate, but it is Brokkr-only (`extends brokkr-fast`), it begins where a branch written by hand begins, and it says nothing about the runs whose work it finishes. Every other recipe (an adopter's own frontier recipe, say) has no later entry. Over 2026-10-18 and 19 one adopter's epic re-drove six runs, each spending 15–25 minutes and a design commit on intake and design before it reached verify.

A recipe already knows which of its phases judge and which write: every driver-bearing site carries a class, `gate` or `work` (decision 0021 ruling 1), and the compiler already walks the table from `initial` to refuse a path to a terminal that avoids the protected phase. What is missing is one word the operator can say at start, `enter`, and the record of what the entered run continues.

## What Changes

- **The entry.** `brokkr run --enter <phase>` starts the run at the named phase of the table it runs under, instead of the table's `initial`. The table, the compiled bundle, its digest, the run manifest and the witnesses do not move: an entry is a fact of the run, journaled, not of the recipe. A recipe whose own `initial` is a gate (`landing`, `preflight`, `review-first`, `verify`) starts as it always did when no entry is named, and its `initial` is itself an entry when it passes admission: `--enter classify` on `landing` is a landing that names the runs it continues.
- **Admission, at compile.** Six facts of the table and its seats, judged in this order, the first that fails named in a typed error with the phase, the fact and the entries the table admits, in the order of the table's `phases` list, before a run id is minted or an event is written:
  1. the phase is one of the table's and is not a terminal, so it is seated;
  2. its name is one the contribution gate prints without a forgery: `^[a-z0-9][a-z0-9._-]{0,63}$`, the dialect's identifier grammar bounded to 64 bytes, applied here so the compiler never admits an entry the gate refuses;
  3. every driver-bearing site of its seat is a gate (decision 0021 ruling 1: a sequence by its steps, each written `gate`, a dialect step included, since an undeclared site is work; a panel by its members; a selector by every case and its default);
  4. the protected phase is the entry itself or is unavoidable from it: the walk the compiler already makes from `initial` (`assert_phase_unavoidable`, decision 0051's constitutional lint), started at the entry;
  5. no work phase is reached from the entry over forward rulings alone, a forward ruling being one whose `next` stands after its `from` in the `phases` list, a park drawing no edge and a self-loop reaching nothing new: so a work phase is reached in an entered run only by a return, which is the commission's "implement is entered only on a return" made mechanical for every work phase;
  6. no seat reachable from the entry needs a journal fact that only a phase the entry skips can set. Two such facts exist: `strategy`, which only the strategy phase's ruling sets (`triage`, decision 0041 ruling 6) and which a `select` with no `default` needs to have a body at all; and the dialect's `{change}`, which only a result of a seat declaring the `change` input carries and which a dialect step that expands it needs. The walk from the entry does not cross the strategy phase for the first, nor a seat declaring `change` for the second, and a selecting seat with no default, or a dialect step expanding `{change}` ahead of any such declaration (the steps of its own sequence counted in order), is a refusal naming the seat or the step and the fact.

  The engine holds no roster of which phases may be entered: the facts are the table's and its seats', and the admitted set is derived by the same six facts. In every `fast`-shaped table that admits `verify` and `review` and refuses `implement` and `ship`. The commission listed `ship` among the gates; it is refused by fact 4 because `SHIP-COMPLETE` reaches `done` without review, so an entry at `ship` would let a run's own journal vouch for a head no seat of that journal judged, which is the one thing the contribution gate rests on. The recovery for a ship that failed is decision 0092's retry when it parked, or an entry at `review`, one judge's read, when it stopped. The `triage`-shaped tables (`triage`, `gpt-flash`, `night-shift`) admit no entry today: `verify` and `review` fail fact 6, since `review` and `implement` select on a strategy only `triage` rules and carry no default; `clarify` and `analyze` fail fact 3, since their dialect `check` steps declare no class and an undeclared site is work; `triage` fails fact 5, since `TRIAGE-CHORE` reaches `implement` forward. The refusal says so, and the road to one is the recipe author's: a `default` case on the selecting seats, named here and not ruled. Brokkr's own re-drive road stays `landing` (decision 0051 ruling 4), which now names the run it continues.
- **The return.** In an entered run a seat receives `returned_from`, the ruling's phase and the result that sent the run there, on its first visit when the ruling that sent it is a return, a ruling whose `next` stands before its `from` in the `phases` list, the order `seat_context` already reads `context.results` in. A forward ruling into a phase this run has not visited hands nothing new, exactly as a first visit does today; a revisit hands what it always did; triage receives nothing on any visit (decision 0041 ruling 6). The rule reads the ruling's direction, never the entry's position, so no table order can send a smith back without the finding. No seat input of a run without an entry moves.
- **The chain.** `--continues <run>`, repeatable and only with `--enter`, names the earlier runs the entered run continues, each a full id, a unique prefix or `latest` in the journal the run is written to. A named run must exist there and be concluded, `completed` or `stopped`: a running one is still at work, and a parked one is resumed or concluded first (decision 0092 ruling 4). A run named twice is refused. Every refusal comes before an event is written. The chain is the operator's word: the engine verifies existence and conclusion and nothing else, and every surface says the chain as named at start. An entry that names no run is admitted: a branch with no run to continue, entered at a gate, is what a landing is.
- **The journal.** `run/started` gains one optional object, `entry`: the phase entered, and the continued runs in the order named, each by its id and the feature its own start recorded, so every reader leads with the words. It is absent on every run without an entry, so every journal written before, and every ordinary run after, is byte for byte what it was. The fold reads nothing of it; the engine reads it at start and at resume to enter the entry instead of `initial`. It is an additive, optional, absent-by-default field under the vocabulary's amended rule (decision 0016's amendment in `contracts/README.md`), as `charters` and `layers` are; its numbered extension schema is minted when the operator accepts decision 0094 (decision 0082 ruling 1), and until then the decision and the Rust type are its shape.
- **What the seats are told.** Every seat of an entered run receives `context.entry`, derived from `run/started.entry`: the phase entered and the continued runs, each by `run_id` and `feature`. It is absent from every seat input of a run without an entry, so those inputs and their digests do not move. The continued runs' results are not handed: the branch, the feature text and the chain are what the seat knows.
- **What the review judges.** The contribution gate vouches the whole branch from its merge-base with the default branch, whichever run or hand wrote it, so that is what a review seat judges. Every review charter whose scope reads "everything since the run began" (`agents/charters/reviewer.md`, `review-correctness.md`, `review-security.md`, `review-adversarial.md`, `node-reviewer.md`, and the pinned copies `recipes/review-first/roles/reviewer.md` and `recipes/standby/roles/reviewer.md`) now scopes the delivery as everything on the branch since its merge-base with the default branch, the cut the anchor makes (decision 0038 ruling 1), which on a fresh branch is everything since the run began, and says that `context.entry` means the branch holds the work of the runs it names and all of it is the seat's to judge. A test holds every charter and copy to the clause. The four panel charters are ones this run executes under; the implementer names the change in its notes.
- **The view.** `RunView` derives `entry` once: the gate entered and the continued runs, each led by its feature with its id after, as named at start. The console's run header, `brokkr ui`, the TUI and `brokkr run`'s plain start line paint it and derive nothing of their own; nothing is painted for a run without one.
- **The gate.** `scripts/delivered-by-brokkr.sh` vouches an entered run as it vouches any run: the ship anchor's per-file patch map is cut from the merge-base of the default branch and the vouched head, so it spans every commit on the branch, whichever run or hand made it, and the tier is cut by the delta since that judgment (decision 0038). The gate reads `entry` from the vouching run's verified journal and names the gate entered and each continued run's id on its check line, never a feature text; an `entry` it cannot read, or a phase outside the grammar admission applied, is a refusal, never a vouch; an absent one reads as today. It fetches no continued run's evidence: a continued run stopped before any anchor existed, and its journal is not required to be published.
- **`landing`.** It stays a recipe, and the design says precisely why: it adds a seat, `classify`, and two rules, which an entry cannot express; it is the by-hand road, where the gate is chosen from the branch's class rather than from the operator's word (decision 0051 rulings 1 and 3); and its `initial` is a recipe's own first phase, which this change leaves untouched. It shares the law: the protected phase is unavoidable from where the run begins, which the compiler held for every `initial` and now holds for every entry. An entry composes over it as over any recipe, admitting `classify`, `verify` and `review`. Decision 0051 ruling 4's road, relighting a judgment that could not land as a landing, keeps its text and gains the chain: the landing names the run it continues, and a stopped run of a recipe that admits its gate is re-driven there instead.
- **Not chosen: the composed landing overlay.** A derived recipe can set `initial` to a gate today; `landing` and `review-first` prove it, and that road stays for by-hand work. It was not chosen as the general mechanism, and decision 0094 records why: an overlay's `initial` cannot be told from a recipe's own first phase, so the compiler cannot refuse an entry at a work phase without a second marker; a recipe is static data and cannot name the runs one re-drive continues; and every adopter would write one overlay per recipe and gate, each restating one word (decision 0071 ruling 5).

## Decisions

The clarify judge returned eight questions on 2026-10-21. Each is answered here, encoded as a requirement or scenario in the deltas, and carried into decision 0094 at design.

- **D1 (Q1, blocking). A skipped phase's fact is an admission fact, never a carried one.** The facts a seat may need from an earlier phase are closed: `strategy`, folded only from the strategy phase's ruling (`fold.rs`, `STRATEGY_PHASE`) and read by `SeatBody::selected` and `computed_inputs`; and `{change}`, carried only by a step result of a seat declaring the `change` input (`engine/sequence.rs`) or a result in `context.results` (`engine.rs`, `nearest_change`). Counters are absent as zero, `reviewed_heads` is set by the protected phase this run visits before ship, and the rest are seat-owned. Option (a), the sixth admission fact, is taken. Option (b), the entry carrying a typed strategy and change, was refused because selection and the `strategy_in` inputs read `RunState`, which is folded from this run's journal alone: the fold would have to read `entry`, and under the amended rule a field a consumer must read to fold correct state is a v2 event, which the frozen `{"const": 1}` of every manifest schema and the closed event-type enum rule out; a synthetic `transition/decided` from triage is refused by the fold's relation, which accepts a decision only at `Decide` after an effect succeeded, and would be a ruling no seat made. Option (c), reading a continued run's fold, fails the same way and would make an unverified chain (D7) a source of selection. Under (a) the triage-shaped tables admit no entry today, said in the refusal; the acceptance case, an adopter recipe that runs intake and design ahead of implement with no selector and no dialect, admits `verify` and `review`, and the acceptance fixture has that shape (D4).
- **D2 (Q2, high). The review judges the branch from its merge-base, and the charter says so.** The gate vouches the anchor's patch map, cut from the merge-base with the default branch (decision 0038 ruling 1), so a review scoped to "since the run began" would rule clean over commits no seat of the vouching run read, and the vouch would stand on nothing. The scope clause of every review charter that reads so moves to the branch since its merge-base with the default branch, the same cut, which costs a fresh-branch delivery nothing because the two cuts are the same commits, and closes the same latent gap in `landing`, whose README already claims the branch is judged against the base. The seats learn the chain from a typed fact present only in an entered run, `context.entry`, which keeps every other run's input byte-identical, and the clause names it. A charter clause is the mechanism because a seat is a model reading its charter: a typed fact alone would not move what it diffs. The refutation offered, that the review already reads the base under decision 0051, does not hold: decision 0051 ruling 1 changed one word of the table and no charter, and the charter text is what the seat reads.
- **D3 (Q3). "Implement is entered only on a return" is fact 5, for every work phase.** Not a recorded departure: an entry from which a work phase is reached forward re-runs design and tasks, the cost the epic exists to remove, and the earlier draft gave no reason. The forward road is defined by the `phases` list, the order the house already reads for `context.results`; a return is a ruling against it. A dialect gate whose steps are written `gate` is refused by it in every table shaped like the dialect's, since its road leads forward to design or implement (the shipped `clarify` and `analyze` fail fact 3 before that, their check steps declaring no class), and a dialect gate placed after implement in an adopter's table is admitted when its road holds.
- **D4 (Q4). Shapes are their phase lists, and the acceptance fixture holds intake and design.** `fast`-shaped: `implement, verify, review, ship, done, stop` (`fast`, `brokkr-fast`, `node`, `release`, `standby`, `review-first`, the three wager harnesses). `panel-review`-shaped: `intake` ahead of the same (`panel-review`, `self`). `landing`: `classify` ahead. `preflight` and `verify`: `verify, review, done, stop`. `research`: `research, verify, done, stop` with `verify` protected. `triage`-shaped: `triage, specify, clarify, design, tasks, analyze, implement, verify, review, ship, done, stop` (`triage`, `gpt-flash`, `night-shift`). The acceptance fixture's table lists `intake, design, implement, verify, review, ship, done, stop`, intake and design being work phases the stopped, continued run entered; so a mutation that starts the entered run at `initial` enters intake and fails the proof, and a mutation that drops `entry` from the journal fails the view and the gate.
- **D5 (Q5). "Before" is the position in the `phases` list, and the return rule reads the ruling, not the entry.** A seat receives `returned_from` on a first visit when the ruling that sent it is a return (`next` before `from` in the list); the entry's own position decides nothing, so a table whose list puts a returned-to work phase after the entry needs no refusal: its smith is still handed the finding. The walk from `initial` was not used to define "before" because every phase of a delivery table is reachable from every other over its returns.
- **D6 (Q6). One grammar for an entry's name, applied at compile and at the gate.** `^[a-z0-9][a-z0-9._-]{0,63}$`: `brokkr_core::policy::is_identifier`, the dialect's change grammar, bounded to 64 bytes as `bounded_site` bounds a label. The compiler refuses a phase outside it as fact 2, so it never admits an entry the gate refuses, and no phase name can forge a check line; a test holds the script's pattern to the compiler's.
- **D7 (Q7). The chain is the operator's word.** `--continues` checks that each run exists in the journal the new run is written to and is concluded, nothing more. A realm or repository check was refused because it would hold only sometimes: the store records no repository, a run started unmapped pins no realm, and decision 0051 ruling 4's road continues a run of another recipe; a check that sometimes passes would be read as a verification it is not. Every surface says the chain as named at start, and the gate prints the ids without fetching them.
- **D8 (Q8). The refusal lists the admitted entries in the order of the table's `phases` list**, the same order facts 5 and D5 read, pinned once per module (decision 0071 ruling 8).

## Left out, and why

- `brokkr rerun --enter`: a rerun is a past run's feature from the beginning. An entered run states its own commission, what the branch is and why, as a landing does (decision 0051), so `--feature` stays required.
- Queueing an entered run: `--enter` and `--continues` live on `brokkr run`; `QueuedLaunch::of` refuses an entry by name rather than widening `queued-launch/v1` in silence. A `queued-launch/v2` waits on a queue that asks for it.
- An entry on a Looper-bound run (`--dispatch`) is refused by name, as a named map is: the v2 manifest lineage and the bridge's normalized `run/started` carry no entry, and a counterpart would be told nothing.
- The continued runs' results are not handed to the entered run's seats (D1): the branch, the feature text and the chain are what a seat knows, as a landing knows them.
- A `default` case for the `triage` recipe's selecting seats, which would let a triage-shaped table admit `verify` and `review`: a recipe change with its own identity move, the author's to propose.
- The fleet list, `brokkr runs` and the bridge's normalized `run/started` (manifest only) are unchanged.
- A landing's first return still receives no `returned_from`: a recipe's own `initial` is not an entry, and this change moves no seat input of a run without one. The return rule of D5 would close it if extended to every run, at the cost of every mid-flight landing's rebuilt input digest; a later story.
- The return bound counts implement visits (decision 0022), so an entered run, like a landing, allows one return more than a delivery. Named, not changed.

## Capabilities

- `gate-entry` (added): the entry, its admission at compile, the first phase, and the return.
- `run-continuation` (added): the continued runs, the journal record, what the seats are told, what the review judges, the run view and the contribution gate.
- `operator-console-read` (modified): the run view names the gate entered and the runs continued.
