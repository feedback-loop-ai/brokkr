# Change: a run of any recipe enters at a gate over work already on the branch, continuing the runs it names (#788)

Status: proposed. The law is decision 0094, proposed; only the operator accepts it.
Change: `2026-10-21-788-enter-at-a-gate`.
Parent story: [#788](https://github.com/feedback-loop-ai/brokkr/issues/788), part of epic [#790](https://github.com/feedback-loop-ai/brokkr/issues/790) (cheaper recovery). Beside it: decision 0092 (#789, on `main`) parks an environment block inside the run so one seat is retried; #787 (decision 0093, in the merge path) retries one panel member. This change recovers the run that has already ended, and keeps clear of both.

## Why

`stopped` is terminal. A run whose work is finished and committed, and which then stopped at a hard rule or exhausted a gate's attempts, has one road back: a fresh run of the same recipe, which begins at the table's `initial` phase, repeats intake and design, and lets the design seat commit again over a branch that already holds the design. The shipped `landing` recipe is `fast` entered at a classify gate, but it is Brokkr-only (`extends brokkr-fast`), it begins where a branch written by hand begins, and it says nothing about the runs whose work it finishes. Every other recipe (an adopter's own frontier recipe, say) has no later entry. Over 2026-10-18 and 19 one adopter's epic re-drove six runs, each spending 15–25 minutes and a design commit on intake and design before it reached verify.

A recipe already knows which of its phases judge and which write: every driver-bearing site carries a class, `gate` or `work` (decision 0021 ruling 1), and the compiler already walks the table from `initial` to refuse a path to a terminal that avoids the protected phase. What is missing is one word the operator can say at start, `enter`, and the record of what the entered run continues.

## What Changes

- **The entry.** `brokkr run --enter <phase>` starts the run at the named phase of the table it runs under, instead of the table's `initial`. The table, the compiled bundle, its digest, the run manifest and the witnesses do not move: an entry is a fact of the run, journaled, not of the recipe. A recipe whose own `initial` is a gate (`landing`, `preflight`, `review-first`, `verify`) starts as it always did when no entry is named.
- **Admission, at compile.** An entry is admitted when the phase is one of the table's and is seated, every driver-bearing site of its seat is a gate, and the protected phase is the entry itself or is unavoidable from it: the constitutional walk the compiler already makes from `initial`, started at the entry. A work phase, a terminal, a phase the table lacks, and a gate from which `done` is reached without the protected phase are refused by a typed error naming the phase, the reason and the entries the table admits, before a run id is minted or an event is written. In every `fast`-shaped table that admits `verify` and `review` and refuses `implement` and `ship`. The commission listed `ship` among the gates; it is refused because `SHIP-COMPLETE` reaches `done` without review, so an entry at `ship` would let a run's own journal vouch for a head no seat of that journal judged, which is the one thing the contribution gate rests on (decision 0051's constitutional lint, `assert_phase_unavoidable`). The recovery for a ship that failed is decision 0092's retry when it parked, or an entry at `review`, one judge's read, when it stopped. A work phase is reached only by the table's own rulings from the gate entered: in `fast`'s shape a return, in `triage`'s shape the forward road once `analyze` finds the artifacts consistent.
- **The return.** In an entered run, the phases before the entry in the table's order are the work the entry took as done on the branch. A seat of such a phase receives `returned_from`, the ruling's phase and the result that sent the run there, on its first visit exactly as any seat does on a revisit, so the smith reads the failing verify or the review's findings it is sent to answer. Today the fact is handed only on a revisit, which an entered run's implementer never is. A phase after the entry is reached forward and receives nothing new. No seat input of a run without an entry moves.
- **The chain.** `--continues <run>`, repeatable and only with `--enter`, names the earlier runs the entered run continues, each a full id, a unique prefix or `latest` in the journal the run is written to. A named run must exist and be concluded, `completed` or `stopped`: a running one is still at work, and a parked one is resumed or concluded first (decision 0092 ruling 4). A run named twice is refused. Every refusal comes before an event is written. An entry that names no run is admitted: a branch with no run to continue, entered at a gate, is what a landing is.
- **The journal.** `run/started` gains one optional object, `entry`: the phase entered, and the continued runs in the order named, each by its id and the feature its own start recorded, so every reader leads with the words. It is absent on every run without an entry, so every journal written before, and every ordinary run after, is byte for byte what it was. The fold reads nothing of it; the engine reads it at start and at resume to enter the entry instead of `initial`. It is an additive, optional, absent-by-default field under the vocabulary's amended rule (decision 0016's amendment in `contracts/README.md`), as `charters` and `layers` are; its numbered extension schema is minted when the operator accepts decision 0094 (decision 0082 ruling 1), and until then the decision and the Rust type are its shape.
- **The view.** `RunView` derives `entry` once: the gate entered and the continued runs, each led by its feature with its id after. The console's run header, `brokkr ui`, the TUI and `brokkr run`'s plain start line paint it and derive nothing of their own; nothing is painted for a run without one.
- **The gate.** `scripts/delivered-by-brokkr.sh` vouches an entered run as it vouches any run: the ship anchor's per-file patch map is cut from the merge-base of the default branch and the vouched head, so it spans every commit on the branch, whichever run or hand made it, and the tier is cut by the delta since that judgment (decision 0038). The gate reads `entry` from the vouching run's verified journal and names the gate entered and each continued run on its check line; an `entry` it cannot read is a refusal, never a vouch; an absent one reads as today. It fetches no continued run's evidence: a continued run stopped before any anchor existed, and its journal is not required to be published.
- **`landing`.** It stays a recipe, and the design says precisely why: it adds a seat, `classify`, and two rules, which an entry cannot express; it is the by-hand road, where no run is continued and the gate is chosen from the branch's class rather than from the operator's word (decision 0051 rulings 1 and 3); and its `initial` is a recipe's own first phase, which this change leaves untouched. It shares the law: the protected phase is unavoidable from where the run begins, which the compiler held for every `initial` and now holds for every entry. An entry composes over it as over any recipe. Decision 0051 ruling 4's road, relighting a judgment that could not land as a landing, keeps its text and gains the better road when a run exists: the run is re-driven at its gate, continuing it.
- **Not chosen: the composed landing overlay.** A derived recipe can set `initial` to a gate today; `landing` and `review-first` prove it, and that road stays for by-hand work. It was not chosen as the general mechanism, and decision 0094 records why: an overlay's `initial` cannot be told from a recipe's own first phase, so the compiler cannot refuse an entry at a work phase without a second marker; a recipe is static data and cannot name the runs one re-drive continues; and every adopter would write one overlay per recipe and gate, each restating one word (decision 0071 ruling 5).

## Left out, and why

- `brokkr rerun --enter`: a rerun is a past run's feature from the beginning. An entered run states its own commission, what the branch is and why, as a landing does (decision 0051), so `--feature` stays required.
- Queueing an entered run: `--enter` and `--continues` live on `brokkr run`; `QueuedLaunch::of` refuses an entry by name rather than widening `queued-launch/v1` in silence. A `queued-launch/v2` waits on a queue that asks for it.
- An entry on a Looper-bound run (`--dispatch`) is refused by name, as a named map is: the v2 manifest lineage and the bridge's normalized `run/started` carry no entry, and a counterpart would be told nothing.
- The continued runs' results are not handed to the entered run's seats: the branch and the feature text are what it knows, as a landing knows them.
- The fleet list, `brokkr runs` and the bridge's normalized `run/started` (manifest only) are unchanged.
- A landing's first return still receives no `returned_from`: a recipe's own `initial` is not an entry, and this change moves no seat input of a run without one. The design may name that gap for a later story.
- The return bound counts implement visits (decision 0022), so an entered run, like a landing, allows one return more than a delivery. Named, not changed.

## Capabilities

- `gate-entry` (added): the entry, its admission at compile, the first phase, and the return.
- `run-continuation` (added): the continued runs, the journal record, the run view and the contribution gate.
- `operator-console-read` (modified): the run view names the gate entered and the runs continued.
