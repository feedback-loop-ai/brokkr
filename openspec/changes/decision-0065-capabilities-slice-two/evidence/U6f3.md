# U6f3 evidence: five seconds for the broker's closing standard error

U6f3 was built on branch `s2/U6f3`, cut from main at `79383713`, in run
`0065-slice-two-unit-u6f3-see-the-8f5f57c2` on 2026-10-17. It closes no task
in tasks.md. It answers requirement MB3 (the broker's end stays bounded)
and the operator's ruling of 2026-10-17 recorded in U6f3's section of
design.md, which prep wrote and this unit keeps unchanged.

## The change

`TOLD` in `crates/brokkr-cli/src/broker/session/stderr.rs` goes from
`Duration::from_secs(1)` to `Duration::from_secs(5)`. Its doc comment names
no value, so it stays as it was. Nothing else in production moves. The
bound is still formed once, in `told`, as `Instant::now() + TOLD`, so it
stays fixed and nothing extends it. No other constant in the broker was
touched. `CLOSING` in `rpc/calls.rs`, the one-second bounds in the
lifetime and readiness tests, and the bound in the `protocol.rs`
integration test are different bounds and stay as they are.

The bound test
`broker::session::stderr::tests::a_sink_that_takes_nothing_is_given_up_on_at_its_bound_and_one_that_reads_takes_it_all`
keeps its form: `Put::Late`, with `taken >= TOLD` and
`taken < TOLD + 500ms`. It gains one assertion,
`assert_eq!(TOLD, Duration::from_secs(5))`. The elapsed check is relative
to `TOLD`, so on its own it cannot tell one second from five, and the
literal pin is what catches a return to one second. The test now takes
about five seconds (the stderr module ran in 5.01s).

## Mutation

With `TOLD` set back to `Duration::from_secs(1)` and the tests left as they
are, `cargo test --locked -p brokkr-cli --lib broker::session::stderr::`
failed one test of ten: the bound test, at `stderr/tests.rs:122`, the new
pin, with `left: 1s` and `right: 5s`. Five seconds was restored and the
same command passed, ten of ten, in 5.01s.

## The handoff test under load

`capability_broker::handoff::a_handoff_that_fails_after_the_lookup_starts_no_server`
ran in the foreground, alone and with no load, and passed in 17.87s. No
`skipped:` line was printed under `--nocapture`, so the boxed and traced
path really ran.

The seat's sandbox refused every outside load generator: a backgrounded
`yes`, `taskset`, and a `bash` script under `.forge/`. So the load ran
inside the test binary. A temporary scratch test, never committed and
removed with `git checkout` before the gates below, started
`2 × available_parallelism` = 48 spinning threads on this 24-core host.
It waited five seconds and then called the handoff test's own function
in sequence, catching each panic so every repetition was counted. It
read `/proc/loadavg` after each call and stopped the spinners at the end.
Before these batches, one libtest run of the named test beside a
60-second, 48-thread spinner also passed. That run took about 62s, and
the 1-minute load average was 35.6 when it ended.

Twenty repetitions under saturation passed, twenty of twenty, plus the
one named libtest run. Each took four to seven times as long as the
unloaded 17.87s. Other work on the shared workstation added to the load
average beyond the spinners. The load stopped when each batch's test
ended. This shows the test passing under CPU saturation. It does not
reproduce CI's exact shape, coverage instrumentation beside strace on a
hosted runner. A control run of the old one-second bound under this load,
to see whether it reproduces the cut line, was not run.
