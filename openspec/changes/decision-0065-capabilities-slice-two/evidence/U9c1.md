## What the grammar reads

The Codex option table (`grammar.rs`, `static CODEX`) gains three options,
measured on codex-cli 0.162.1:

| Option | Shape | Effect |
| --- | --- | --- |
| `--ignore-user-config` | switch | `Control(Power::Mcp)`, as Claude's `--strict-mcp-config` is |
| `--disable` | one value, split or `=`-joined, repeatable | `Control(Power::Mcp)` |
| `--enable` | the same shape | `Control(Power::Tools)` |

Each is capability-bearing, so an authored one keeps slice one's refusal:
compile's `authored_refusal`, the inline launch judgment and the pins check
refuse it as they refuse every other catalogue control. `CAPABILITY_TABLES`
gains `permissions` and `default_permissions`, so an assignment into either
is a capability assignment wherever it is written, never the
unclassified-key refusal it was.

The private child `grammar/config.rs` reads the isolation. `isolation` maps
a node: `--ignore-user-config` to `Isolation::UserConfig`, `--disable` of
exactly `apps` or `plugins` to `Isolation::Apps` or `Isolation::Plugins`,
any other `--disable` to `Unisolated::Disabled`, and any `--enable` to
`Unisolated::Enabled`. `profile` reads a command's one permission profile:
exactly one canonical `permissions.<name>={filesystem={…}}` definition,
then exactly `default_permissions="<name>"` selecting it, and no `--sandbox`
(every spelling, since the grammar folds `-s`, `-sCLASS` and
`--sandbox=CLASS`) and no `sandbox_mode` assignment anywhere in the
command. The filesystem table is read entry by entry, each
`"<path>"="<access>"` a quoted string with no escape and no control
character, joined by single commas with nothing around them. The access
vocabulary is closed to `read`, `write` and `deny`.

### The bound reading (operator ruling 4 of 2026-10-23; run 1's H1)

Run 1 read the profile by its shape: any absolute `"write"` path counted as
the workspace and any `"deny"` as the store, so
`{":root"="read","/"="write","/nonexistent"="deny"}` passed. The reviewers
rejected that, and so does ruling 4. Run 1's evidence recorded the
structural reading as an assumption; that assumption is withdrawn.

`profile` now takes a `grammar::Bound` (crate-private): the seat's
workspace root and the secrets store's path that the final check is handed
beside the workdir. `rendering` admits exactly one closed rendering and
compares exact strings, never resolving a path, because the crate is pure.

| Entry | Read |
| --- | --- |
| no store handed (`Bound::store` is `None`) | every profile refuses, `Unisolated::Unhanded` |
| `":root"="read"` | required, once |
| `"<workdir>"="write"` | admitted; renders `workspace-write`. Without it the profile renders `read-only` |
| `"<store>"="deny"` | required, once |
| a `"write"` of any other path, `:root` included | `Unrooted` |
| a `"deny"` of any other path, a second deny among them | `Unstored` |
| a `"read"` of any path but `:root`, a path named twice, no `":root"="read"` | `Classless` |
| the store not denied | `Undenied` |

`native_controls::Serving` gains one public field, `store: Option<&'a str>`.
Every struct literal of `Serving` in the workspace ends `..Default::default()`
or `..chosen` (workspace clippy and every suite compiled unchanged), so
production hands `None` until U9c2 sets it. Production therefore refuses
every profile in a final command until then, which is fail-closed.
`Serving::bound` (in `read.rs`) pairs it with the workdir. `check_final`
passes that bound to every `read_state` it makes: the final command, the
recomposition, and in `sealed_inputs` the recipe's words and pins, the
template, the hands, the boundary, the local sandbox fragment and the
plan's native controls.

`read_state` (the private child `native_controls/read.rs`) reads the
profile first, then expresses its class as `Expressed::Class` where the
selector stands. The definition expresses nothing of its own. Each
isolation option is the effect `Expressed::Isolation`, so the final check's
`carried` comparison requires each option the sealed plan composes, and a
lost one refuses before any rebuild ("does not carry the isolation option
'--disable apps' as its sealed plan composes it").

`mcp::untransported` now takes the bound too. Its Codex class is
`named("--sandbox") || profiled()`, and `profiled` is
`grammar::profile(hands, bound)` reading `Ok(Some(_))`, so only the bound
profile carries the class. The three `mcp_servers.brokkr` bindings stay
required. The composer (`compose_or_exclude`) is handed no store's path,
and passes `Bound::default()`. Its public signature has a caller in
`crates/brokkr-runtime/src/capabilities.rs`, outside this row, and moving
its CC-38 body to a renamed function would read as a new function over the
CC ceiling. So in this unit a profile in the box's hands carries no class
at composition: compile, and the final check's own recomposition, refuse it
as hands without their sandbox class. That is fail-closed. Handing the
composer the store is owed with U9c2's builders (see Follow-ups).

### Faults

Each fault is a variant of the typed `Unisolated` (thiserror). Its text
names the argument and fixed words only, never a value:

| Variant | Refused |
| --- | --- |
| `Enabled` | any `--enable` |
| `Disabled` | `--disable` of anything but `apps` or `plugins` |
| `Dotted` | a key under `permissions.<name>.` |
| `Unprofiled` | any other `permissions` value: the whole table, another table, a quoted or spaced key, a value with space around `=` or between entries, an unquoted access, an empty, escaped or control-character path, trailing text |
| `Access` | an access other than `read`, `write`, `deny` |
| `Unhanded` | any profile where no store's path is handed |
| `Classless` | no `":root"="read"`, another path read, a path named twice |
| `Unrooted` | a write of a path other than the workspace root |
| `Unstored` | a deny of a path other than the store |
| `Undenied` | a profile that does not deny the store |
| `Selector` | any other `default_permissions` value, or a selector before its profile |
| `Twice` | a second profile or a second selector |
| `Unselected` | a profile no selector selects |
| `Beside` | a profile beside `--sandbox` (all spellings) or a `sandbox_mode` assignment (all `-c` spellings), on either side |

## Moved to U9c2 by ruling 4

Two of the controller's items are U9c2's under the operator's ruling 4 of
2026-10-23, and this unit does not implement them.

The first is the inline launch judgment, `judge_inline_codex_launch`
(`grammar.rs`, called from brokkr-runtime `engine.rs` and `bundle.rs`). It
is unchanged. It admits only the engine's `--sandbox` fragment or its
rejoin `sandbox_mode`, and refuses the isolation options and both
permission tables as capability-bearing controls. U9c2 hands it the
workspace root and the store's path.

The second is the whole rejoin check accepting a profile. `codex_rejoin`
(`adapters.rs`) still takes the class from `--sandbox`, so a profile-only
rejoin keeps declining "sandbox-unavailable" until U9c2's rejoin builder
emits the profile. This unit proves acceptance and each refusal on rejoin
commands through the grammar's own reading (`profile` and `read_state`),
as the ruling directs.
