# U4a2: driver-supplied attribution erased at the engine edge (tasks 13.3–13.4)

Run `0065-slice-two-unit-u4a2-see-the-19cfaa84` built U4a2 on branch
`s2/U4a2` from main at `ac5292b0`. It changed one of the row's two
production files, `crates/brokkr-runtime/src/engine/checkpoints.rs`, and
left `engine.rs` untouched.

## What changed

`checkpoints.rs` gains one private table, `ATTRIBUTION`, naming the five
CC1/SC4 attribution fields (`capability`, `dialect`, `call_id`,
`call_state`, `response_sha256`), and one private function,
`without_driver_attribution`, that removes those keys from a checkpoint
object and passes anything else through unchanged. `Checkpoints::offer`
calls it first, before a checkpoint is held, counted or appended. `tool`
is legacy telemetry and is not in the table.

The erasure sits in `offer` rather than at each sink because `offer` is
the one door both sinks use. engine.rs's single-site sink (`run_driver`,
`sink.offer("", …)`) and its panel sink (`run_panel`'s receive loop,
`sink.offer(&member, …)`) both journal live driver checkpoints only
through it. So one table holds the vocabulary (decision 0071 ruling 5), and
a later caller of `offer` cannot skip the erasure. engine.rs needed no edit,
which also keeps it at its 4,862-line baseline. Nothing new is emitted: the
function only removes keys.

## Telemetry paths that reach append

The audit grepped every `EffectCheckpointed` append and every caller of
the two sinks in `crates/` (non-test code).

| Path | What it appends | Reaches `offer`? |
| --- | --- | --- |
| `engine.rs` `run_driver`, called from the seat path (`engine.rs:1512`) and sequence steps (`sequence.rs:291`, `:406`) | live driver checkpoints, single-site | yes |
| `engine.rs` `run_panel`, called from panel seats (`engine.rs:2176`) and sequence panels (`sequence.rs:343`) | live member checkpoints | yes |
| `engine.rs` `journal_panel_members` (`self.append`) | the engine's own `panel-member-finished` marker, built from literal keys | no; the engine writes every key itself |
| `sequence.rs` `checkpoint_step` (`self.append`) | the engine's `sequence-step-finished` marker, wrapping the step result under `result` | no; this is the step-result seam, out of scope by the framing |
| `brokkr-protocol` `oneshot.rs` | collects checkpoints in its report and journals none | n/a |
| `brokkr-bridge` | reads and redacts journaled checkpoints, appends none | n/a |

No other telemetry path appends a checkpoint.

## Tests and removal controls

The new child module `crates/brokkr-runtime/src/engine/checkpoints/tests.rs`
(128 lines, registered from `checkpoints.rs`) holds the proof. Both owning
suites sit at their file-lines baselines (tests.rs 6,681, boundary_tests.rs
4,620), so the proof went into a child module. Its only edit to tests.rs is
size-neutral: `panel_input` became `pub(super)` so the child can reuse it.
The fixtures reuse `engine::tests`'s builders (`engine`, `single_body`,
`member`, `panel_input`, `checkpointing_command`). Each driver is a real
`sh` process speaking the driver protocol over its pipes, through the
engine and the store's v5 append fence. It streams a legacy row (`step`,
`turn`, `model`, `effort`, `input_tokens`, `output_tokens`, `tool`, `target`,
`harness`) and then the same row with a complete forged group whose
`response_sha256` is 64 lowercase hex characters.

- `a_single_site_driver_cannot_journal_capability_call_attribution` drives
  `run_driver`. Its assertion at line 90 compares the whole stored
  checkpoint list to two identical legacy rows carrying only the engine's
  `boundary` stamp. Its assertion at line 91 checks that the report carries
  no refusal.
- `a_panel_member_cannot_journal_capability_call_attribution` drives
  `execute_panel`. Its assertion at line 111 compares the whole stored list
  to the two identical member-tagged legacy rows followed by the engine's
  exact `panel-member-finished` marker.

The assertions compare stored records, not a schema verdict or the helper's
output. Under v5 a surviving field makes the fence refuse the row, so the
stored list is one row short. Under v6, once U4b admits a complete group, a
surviving field would be stored. Either way the list differs from the
expected one, so the same assertion binds after U4b.

Each mutation compiled, was run with
`cargo test -p brokkr-runtime --lib engine::checkpoints::tests`, and was
restored. All four were re-run against the final test text.

| Mutation in `checkpoints.rs` | Single-site test | Panel test |
| --- | --- | --- |
| M1: `offer` no longer calls `without_driver_attribution` | FAILED at :90 (only one row stored) | FAILED at :111 |
| M2: `response_sha256` dropped from `ATTRIBUTION` | FAILED at :90 | FAILED at :111 |
| M3: `capability` dropped from `ATTRIBUTION` | FAILED at :90 | FAILED at :111 |
| M4: `tool` added to `ATTRIBUTION` (legacy over-erased) | FAILED at :90 | FAILED at :111 |

The single-site refusal assertion (line 91) was bound separately. On an
earlier draft it ran before the stored-list assertion, and M1 failed it with
`left: Some(Failed { error: "seat record at journal seq 3 violates
contracts/seat-record.v5.schema.json at /" }) right: None`. The assertions
were then reordered so the v6-proof stored-list assertion fails first. After
restoring, both tests pass.

After CI's exact coverage gate found `without_driver_attribution`'s
non-object arm unexercised, the controller added
`a_checkpoint_that_is_not_an_object_passes_unchanged`, which hands the
helper a null, a string and an array holding an attribution key and asserts
(line 123) that each comes back equal to what went in; the re-vouch run
`0065-slice-two-unit-u4a2-see-the-ce36b078` bound it by turning that arm
into `_ => Value::Null`, which failed it at line 123 on the string
(`left: Null`, `right: String("seat-turn")`), and re-ran M1 against the
same text, which failed the two sink tests at lines 90 and 111 again.

## Follow-up for U4e

U4e stamps the engine's own attribution group at these sinks. Because the
erasure runs inside `offer`, U4e must add its group after the erasure, for
example through a separate engine-owned argument to `offer`. If it stamped
the group before calling `offer`, the group would be removed.
